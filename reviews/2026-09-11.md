## Flim/Services/ShareBreadcrumbs.swift:36 (medium)

`occurred_at` is stamped with `Date.now` after the `await supabase.auth.session` suspension point inside a fire-and-forget `Task`, so each row's timestamp reflects when that particular async insert happened to get scheduled, not when the event actually occurred on device. The elapsed-time text embedded in `line` (t+X.XXs, built synchronously before the `Task`) stays correctly ordered, but `occurred_at` is the column the diagnostic query in docs/PENDING.md sorts by ("select occurred_at, detail from crash_diagnostics where kind = 'breadcrumb' order by 1"), and schema.sql documents `occurred_at` as specifically meant to reflect real event time, distinct from `created_at` (upload time).

Failure scenario: two breadcrumbs fire in true order, "pager.share.tap" then a few milliseconds later "sheet.onAppear" (this is exactly the shape PENDING.md describes: several log calls within 60ms of each other). Each call spawns its own unstructured `Task`, and each independently awaits `supabase.auth.session` before writing `occurred_at: .now`. If the tap's task's session lookup takes longer than the sheet's (a token refresh, or just executor scheduling under concurrent load), the sheet's row gets an earlier `occurred_at` than the tap's row despite happening after it. Reading the rows back "order by occurred_at" then shows the sheet appearing before the tap was ever pressed, the opposite of what happened, on the exact tool built to nail down this class of ordering bug.

Fix direction: capture `let occurredAt = Date.now` synchronously before entering the `Task`, and use that in `Insert` instead of `.now`.
