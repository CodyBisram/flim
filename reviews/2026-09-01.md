## 1. `admin_overview()`'s never_asked_notifications does not match the definition its own comment claims

**File:** `supabase/migrations/2026-08-31_admin_overview_v2.sql:88-92` (same block also in `2026-08-31_admin_overview.sql:941-946`)
**Severity:** medium

The comment above this field says "Everyone the notification prompt never reached ... the ABSENCE of both decisions. The same definition admin_reach uses." But `admin_reach()`'s `never_asked` (`supabase/migrations/2026-08-19_admin_analytics.sql:111`) is `count(*) from people where not said_yes and not said_no`, which only checks for the absence of a `notifications_authorized`/`notifications_denied` activation event. The new query adds an extra condition the sibling function does not have: `NOT EXISTS (... device_tokens ...) AND NOT EXISTS (... activation_events ...)`.

**Failure scenario:** a user who holds a `device_tokens` row (registered for push independently of the permission prompt, or a token left behind after later revoking notifications in Settings without the app recording a fresh `notifications_denied` event) but has no `notifications_authorized`/`notifications_denied` row is counted in `admin_reach().never_asked` but excluded from `admin_overview().never_asked_notifications`. The two dashboard panels then show different counts for what the migration documents as the same measure, and the Overview panel's "Worth acting on" card (which flags this number as "cannot be pulled back by a reveal") undercounts the group it exists to surface.

## 2. Reveals week-over-week comparison in `admin_overview()` compares an 8-day window to a 7-day window

**File:** `supabase/migrations/2026-08-31_admin_overview_v2.sql:31-32,58-61` (same block also in `2026-08-31_admin_overview.sql`)
**Severity:** medium

`d0 = current_date - 7` and the reveals "now" bucket is `day >= d0` with no upper bound, so it includes every day from `current_date - 7` through `current_date` inclusive, which is 8 distinct calendar days. The "prev" bucket, `day >= d1 AND day < d0`, covers `current_date - 14` through `current_date - 8`, which is exactly 7 days. The two windows are not the same length, so they are not comparable, even though the Overview panel labels this "the last 7 days, each number against the 7 before it."

**Failure scenario:** with `reveal_watched` volume flat day over day, `reveals.now` will still sum roughly one extra day of `occurrences` versus `reveals.prev`, making the week-over-week delta shown on the dashboard read as growth (a green up arrow) when nothing changed. The same migration gets the equivalent math right two sections later for `signups_daily`, which correctly uses `current_date - 13` for a 14-day inclusive window, so this looks like an off-by-one rather than an intended asymmetry.
