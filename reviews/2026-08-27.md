# Review notes for Aug 27

Covers the 16 commits on main from the last 24 hours (8a8f626..580bd80).

## 1. Flim/ContentView.swift:109

The new UndoCenter.shared.flush() call on account change never actually runs on a real sign out, so a pending undoable action (block, delete, report) can commit later against a mismatched or already-reset feed.

Failure scenario: user deletes or blocks something, which stages a 5 second undoable action, then signs out within that window. AuthService.signOut() posts .flimAccountDidChange from a defer block that runs after the Supabase session is already invalidated. NotificationCenter delivers this synchronously, so ContentView's .onReceive(.flimAccountDidChange) handler runs immediately, sets cachedAccountId = nil, and calls feed.resetForAccountChange() (feed.feed = []) without ever calling UndoCenter.shared.flush(). By the time SwiftUI later runs .onChange(of: auth.currentUser?.id), cachedAccountId is already nil and matches newId, so the guard bails out and the flush() at line 109 never executes. The originally staged item's own independent 5 second timer still fires later, calling commit() against an invalidated session. If commit() returns false, revert() runs, which for a block or delete is FeedService.restore(_:), appending the removed items back into feed.feed. If the same device signs into a different account before that timer fires, the reload has already repopulated feed.feed with the new account's posts, and the stale revert then appends the departed account's posts into it, so one account's content can appear in another account's feed.

Severity: high.

## 2. Flim/Views/Rolls/RollsView.swift:357-362

"Shoot into this roll" posts a bare NotificationCenter notification instead of going through CameraRollSelection, so the camera can silently point at the wrong roll.

Failure scenario: CameraRollSelection.select(_:for:) exists specifically because a NotificationCenter post alone is lost whenever CameraView is not currently mounted, which is the normal case when tapping this button from the Rolls tab. Both other call sites that need to point the camera at a roll (CreateRollView.swift:167 and JoinRollView.swift:140) call CameraRollSelection.select, which persists the choice to UserDefaults and posts the notification, so CameraView.restoreSelectedRoll reads the correct roll on next appearance even if it was not mounted at post time. The new button in RollsView instead posts .selectCameraRoll and .openCamera directly, with no persistence. If CameraView is not already mounted, the notification is delivered to nobody, the tab switch mounts a fresh CameraView, and restoreSelectedRoll falls back to whatever roll id was last persisted (a different roll, or Personal). The user taps a button labeled "Shoot into this roll" for roll B and the next photo they take can land in roll A instead, with no indication anything went wrong.

Severity: high.

## 3. Flim/Views/Feed/FeedView.swift:406 (via FeedUnitCard.swift onAuthorBlocked)

Blocking an author re-snapshots the unread ledger in full instead of growOnly, which can make the header's unread count shrink or an already-open unit disappear, contradicting the ledger's own "never ticks down as you read" invariant.

Failure scenario: snapshotLedger(growOnly:) at FeedView.swift:686 sets ledgerContributions = growOnly ? mergedLedgerContributions(counted:fresh:) : fresh. The merged, growOnly path is what preserves a unit's already-counted contribution even after the reader finishes it, so the header count only ratchets up. onAuthorBlocked (FeedUnitCard.swift:689, wired at FeedView.swift:406) calls snapshotLedger() with growOnly defaulting to false specifically so stale references to the blocked author's now-removed unit are purged from clearedUnitIDs and the caught up seam. But the same non-growOnly call also resets ledgerContributions = fresh, which is a plain re-derivation from the current feed, not a merge, so any other, unrelated unit that was already fully read (and thus dropped out of "fresh") loses its previously counted contribution too. Concretely: load the feed, read all of a friend's unit so the header still correctly shows its count via the ratchet, then block an unrelated third author. The header's shot and friend count can visibly shrink even though nothing the user read has changed, and per the code's own documented 04:00 boundary reasoning for why growOnly must intersect rather than replace, a unit that was fully read just before 4am and stayed open past it can vanish out from under the reader the moment they block someone else, not only on an explicit catch up moment as the design intends.

Severity: high.

## 4. Flim/Views/Profile/BadgePickerSheet.swift:643-660

Saving a badge selection has two uncoordinated write paths to the same data, so a stale deferred "clear badges" action can silently overwrite a badge selection saved moments later.

Failure scenario: when Custom mode has nothing picked, save() stages the clear through UndoCenter.shared.stage with a 5 second window and dismisses immediately (line 652-657). Any other save goes through commit() (line 662), which calls auth.setDisplayedBadges directly and never touches UndoCenter, so it neither flushes nor cancels a pending staged clear. Sequence: user clears all badges and taps Save (stages an empty selection, 5 second timer starts). Within that window the user reopens Badges, picks two badges, and taps Save again; order is non-empty so this goes through commit() directly, awaits successfully, and the user sees badges applied. The first action's independent timer, untouched by the second save, still fires on its own schedule and calls apply([]), reverting the user's just confirmed selection back to no badges, with no error and no visible cause.

Severity: high.

## 5. Flim/Views/Rolls/RollsView.swift:398-406 and 733-739

The active roll's meta line can say "none of them yours" for a roll the user has actually shot into, because two frame counts are written by sequential awaits and a render can land between them.

Failure scenario: refreshFrameCounts(userId:) writes frameCounts[roll.id] first, then awaits a second network round trip before writing myFrameCounts[roll.id]. Both are separate @State dictionaries, so SwiftUI can render activeMeta(_:) in between the two writes. During that window frames > 0 is already true (from the first write) but myFrameCounts[roll.id] is still nil, so mine defaults to 0 and the line reads "none of them yours" even for a user who has shot frames into that roll. It self corrects once the second await resolves a moment later, but every cold load or pull to refresh of the active roll can show this transient false claim.

Severity: medium.

## 6. Flim/Views/Feed/UserPageView.swift:246-266

blockAccount() defers dismiss() into the block's commit closure, which can fire the deferred dismiss up to 5 seconds after the tap and pop whatever the user has since navigated to.

Failure scenario: dismiss is captured as leave at block time (line 254) but only invoked inside commit, which runs either at natural 5 second expiry or whenever UndoCenter is flushed early (backgrounding, another staged action, or an account change). The page is designed to stay interactive during that window. If the user pushes further navigation from this same page during the window, for example opening a follower's profile, and the block resolves afterward, leave() pops this page's position in the stack at that later moment, which can discard whatever the user pushed on top of it in the meantime.

Severity: medium.

## 7. Flim/Views/Profile/ProfileView.swift:501-507

The photo error banner's auto-dismiss timer does not cancel a previous timer, so a second distinct error within the window can be cleared early by the first error's leftover timer.

Failure scenario: .onChange(of: photoError) spawns a fresh 2.6 second Task every time photoError changes, with no cancellation of any previously spawned Task. If an avatar save fails and, before 2.6 seconds pass, a cover photo save also fails with different text, both timers exist independently. The first timer still fires at its original deadline and clears photoError, cutting the second error's visible time short instead of giving it a fresh 2.6 seconds.

Severity: low.
