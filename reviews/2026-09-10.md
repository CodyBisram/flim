# Review notes, Sep 10

Covers commits on main from the last 24 hours (63e69a5..a3d1478).

## 1. FeedService.swift:974, high

The final write guard in `loadMoreFeed` checks only `AccountEpoch.isCurrent(epoch)`, not `generation == feedGeneration`, even though this same diff added `feedGeneration` and changed the guard a few lines above (line 926) specifically to drop a stale in-flight page's writes, and even though `loadMoreFeed`'s own comment (line 858) says a refresh now proceeds while an older page is in flight because "that older page is dropped by the generation check when it lands."

Failure scenario: pull-to-refresh call A bumps `feedGeneration` to 5 and starts fetching. While the per-item loop's mid-flight guard (line 926) still passes, the user triggers a second refresh, call B, which bumps `feedGeneration` to 6 and completes first, writing the current feed. Call A then reaches line 974, where only the epoch is checked, passes, and overwrites `feed`, `reactionsByPost`, `commentsByPost`, and `tagsByPost` with its own stale generation 5 results, silently reverting the feed to older content.

## 2. Flim/Views/Rolls/RollRevealViewModel.swift:170-182, high

Dead frames are filtered out of `playedDeck` (line 173) but stay in `deck`. When `playedDeck` comes up empty the view sets `isEmpty = true` (line 178), which `RollRevealView.swift:95-96` routes to the empty state whose text (`RollRevealView.swift:655`) reads "The shots in this roll were deleted."

Failure scenario: a roll whose only surviving photo(s) are flagged `isDeadFrame` (a real capture-time "Missed?" verdict from `BurstDetector`, not a test-only flag) develops normally, since `deck` is non-empty and the roll's own grid shows the frame with its "Missed?" label. Opening the reveal, though, tells the person their shots were deleted, with a dismiss button, when nothing was deleted; the same frame is still visible and openable from the roll's photo grid seconds later. This contradicts the diff's own stated intent for `PhotoGridCell`, that a dead frame gets "a label, not a hide."

## 3. supabase/functions/send-daily-digest/index.ts, high

`2026-09-09_push_run_locks.sql` was added this window specifically to stop two overlapping cron runs of a push sender from both reading the same unsent rows and both sending; `send-develop-push` and `send-social-push` were wired to `acquire_push_lock`/`release_push_lock` in this diff, but `send-daily-digest` was not. It still reads all of `digest_state` into memory up front, loops sending pushes, and only afterward upserts `digest_state` per user, with no lock around any of it.

Failure scenario: `flim-daily-digest` fires hourly via `net.http_post`, which is fire-and-forget and provides no serialization on its own. If one hourly run is still mid-loop (slow APNs calls across many recipients) when the next tick fires, both runs read the same stale `digest_state.last_sent_at` for a given user, both decide that user is eligible, and both send a digest push before either writes back `digest_state`, so the user gets two digest notifications for the same window.

## 4. Flim/Services/AuthService.swift:474-499, medium

`setAccent` has no `AccountEpoch` guard at all, unlike the other write paths in this file, and resolves the target user from `try await supabase.auth.session` at completion time. `reconcileAccent`'s `.uploadLocal` branch (line 496) fires it from an uncaptured `Task` with no epoch check either.

Failure scenario: this codebase already supports sign-out-then-sign-in-as-a-different-account without a restart via `AccountEpoch`. If that switch happens while account A's background `setAccent` upload is still awaiting the session or the update, the fetched session now belongs to account B, so the update writes account A's leftover local color onto account B's row, and the trailing `currentUser?.accentColor = name` (now B's `currentUser`) overwrites B's just-loaded accent with A's stale pick. A narrower same-account variant: a user picks a new accent right after launch while the automatic reconcile is still uploading the old local pick; whichever write lands last silently wins.

## 5. supabase/functions/send-develop-push/index.ts:249, medium

`acquire_push_lock` is called with `p_seconds: 240` for the `develop` lock, but `flim-develop-push` runs every 5 minutes (300s), a longer interval than the social push's matching 2-minute schedule against its own 240s lease.

Failure scenario: a develop-push run that takes longer than 300 seconds (plausible when several large rolls each send pushes serially per device token) has its lock silently expire at the 240s mark, so the next scheduled tick's `acquire_push_lock` call succeeds and starts processing the same unsent `photos` rows concurrently with the still-running original, sending duplicate "roll developed" pushes to the same roll members.

## 6. Flim/Views/Feed/FeedView.swift:462 and Flim/Views/Rolls/RollsView.swift:230, medium

`FirstVisitLine` is designed to stay visible for a new account's whole first visit to a surface and mark itself seen in `onDisappear` (its own doc comment), but in both Feed and Rolls it is placed directly inside a `LazyVStack`, whose children can be torn down and recreated as they scroll out of and back into the visible region. Other call sites of the same component (`DarkroomView`, `UserPageView`, `RollDetailView`) sit in a plain, non-lazy container and do not have this problem.

Failure scenario: a new account opens Feed, sees the first-visit sentence, scrolls down one screen so the banner leaves the visible region, which fires `onDisappear` and marks the surface seen. Scrolling back up re-fires `onAppear`, which now computes `nil` since it is already marked seen, so the line disappears mid-visit instead of staying for the whole first visit as intended.

## 7. Flim/Services/Activation.swift:82-109, medium

`Activation` is deliberately not actor-isolated, so `log`'s enqueue path and `flushPending`'s drain loop can run concurrently and each do a non-atomic read-modify-write on the same UserDefaults array key: `flushPending` captures `remaining = pending()` once into a local variable and later writes `store.set(remaining, ...)` after removing an entry, without re-reading the store first.

Failure scenario: at launch, `flushPending` reads `remaining = ["first_launch"]` and awaits sending it. Concurrently, a capture calls `Activation.log(.firstShot)`, whose send fails, so it calls `enqueue("first_shot")`, which reads the still-unchanged store, `["first_launch"]`, and writes `["first_launch", "first_shot"]`. `flushPending`'s send then succeeds, and it writes back its stale local `remaining` with `"first_launch"` removed, `[]`, clobbering the enqueue's write and silently losing `"first_shot"` forever, the exact "dropped first" case this queue exists to fix.

## 8. Flim/Views/Rolls/RollDevelopAskSheet.swift:24-25, low

`timeLabel` decides "same day" with `Calendar.isDate(_:inSameDayAs:)`, a midnight-boundary comparison, while the rest of the app groups days on FLIM's 4am boundary (`FeedUnit.dayKey`). `Roll.developDelay` is a fixed 12 hours, so a roll created in the evening can develop after midnight but before 4am.

Failure scenario: a roll created at 3 PM develops around 3 AM the next standard-calendar day. `FeedUnit.dayKey` would still call that moment part of the prior day, since it is before the 4am rollover, but this label instead reads the new weekday, "Saturday at 3:00 AM," an inconsistent notion of "day" for the same timestamp shown to the person who just created the roll.

## 9. Flim/Views/Profile/ChapterRecapViewModel.swift:227-237, low

Dead frames are filtered out of the provisional deck and out of `ChapterCuration`'s own candidate pool, but `highlightIds` (from server stats `mostReacted`, `mostCommented`, `longestGap`) are unioned into `pickedSet` against the unfiltered `photos` array, and `curatedDeck` filters that same unfiltered array.

Failure scenario: `longestGap` is a purely time-based stat, indifferent to frame quality. If a dead-frame photo happens to be the month's longest gap, it is force-included back into the final chapter recap deck, the one place in this diff where such a frame is not even labelled "Missed?".
