# Review notes for Sep 6

Scope: the 13 commits landed on main in the last 24 hours (6d8729f through b531711), covering the Chapters stats/curation work, the roll-navigation dedup fix, the retry-pill fix, the flash-falloff Lanczos clamp, and the pg_net vacuum migration.

## 1. `Flim/Views/Main/MainTabView.swift:116` and `Flim/Views/Rolls/RollsView.swift:341,360,484,617` (high)

`rollsPathIds` is documented as being "kept in lockstep with `rollsPath` itself" (MainTabView.swift:30-32), and `rollsPathAction` (MainTabView.swift:41-44) relies on that array to decide whether a push-notification-driven roll push should append a new `RollDetailView` or pop back to an existing one (MainTabView.swift:486-494). But `rollsPathIds` is only appended to at the four manual push call sites inside `MainTabView` (lines 329, 355, 376, 402). `RollsView` pushes roll rows onto the very same `rollsPath` via `NavigationLink(value: roll)` (RollsView.swift:341, 360, 484, 617), routed through `.navigationDestination(for: Roll.self)` (RollsView.swift:168-170), and neither that path nor an ordinary back-swipe/back-button pop ever touches `rollsPathIds`. The two trackers can silently diverge from the real navigation stack.

Failure scenario A: user opens Roll A by tapping it in the Rolls grid (ordinary `NavigationLink`, `rollsPathIds` untouched). A push notification for a new comment on Roll A arrives while A is open. `rollsPathAction(for: A, pushedRollIds: rollsPathIds)` finds A not present and returns `.append`, so `rollsPath.append(roll)` pushes a second `RollDetailView` for A on top of the first. This reproduces the exact duplicate-instance / shared `pendingRollPhoto` race this feature says it was written to fix (both instances' `onChange` handlers race to consume the same intent, and the buried one can win).

Failure scenario B: user opens Roll A via a push (`rollsPathIds == [A]`), then backs out normally (swipe-back). The real stack is now empty but `rollsPathIds` still says `[A]`. A later push for Roll A computes `.popTo(keepingFirst: 1)`; the truncation loop (`while rollsPathIds.count > keepingFirst`) does nothing since count is already 1, and the roll is never appended to `rollsPath` at all. The push silently fails to open anything.

## 2. `Flim/Services/RemotePush.swift:111` (medium)

`claim(_:)` unconditionally calls `NotificationService.cancelAllRollDevelopNotifications()` on every successful device-token registration, cancelling every pending local develop-roll reminder for the account, not just one scheduled during the specific race the adjoining comment describes (a capture whose local reminder was scheduled just before this same registration round trip landed). `claim` has no re-entrancy guard beyond `registeredAccountId`, which resets to `nil` on every process launch, and it is reached from `reclaimForCurrentAccount()`, which `ContentView` calls on every launch/foreground resolve where a user is signed in, with no equivalent to the guard `ContentView` itself applies to its own cancellation call (`if previousId != nil`, ContentView.swift:137).

Failure scenario: user captures a roll while offline or before push registration completes, so a local develop-time reminder is scheduled as a fallback. Later in the same session, or on a routine relaunch, `reclaimForCurrentAccount` succeeds and cancels that reminder along with every other pending one for the account, even though the roll it was for has nothing to do with the registration race. If the server-side push then fails to reach the device for any reason before develop time (APNs delivery failure, connectivity, server hiccup), the user gets no notification for that roll at all, because the only fallback was just swept away on an unrelated relaunch.
