## 1. Chapter recap pager reads and writes the wrong reactions/comments table

`Flim/Views/Profile/ChapterRecapView.swift:299-317`

The recap pager is opened with `showsReactions: true, showsComments: true`. `PhotoPagerView`
resolves and mutates reactions/comments purely by `photoId`, through
`PhotoService.fetchReactions(photoId:)`, `fetchPhotoComments(photoId:)`, and
`addReaction(photoId:...)` (`Flim/Views/Components/PhotoPagerView.swift:1830-1957`,
`Flim/Services/PhotoService.swift:1327-1428`), all of which read and write
`public.photo_reactions` / `public.photo_comments`. But `chapter_stats()`
(`supabase/migrations/2026-09-04_chapter_stats.sql:39-49, 143-189`) explicitly documents that a
chapter's "most reacted", "most commented" and "reactions received" numbers are computed from
`public.post_reactions` / `public.post_comments`, the feed-post tables, precisely because
`photo_reactions` / `photo_comments` back the separate roll-photo thread and are never joined
into a feed card's own counts.

Failure scenario: a posted photo accrues 12 feed likes (`post_reactions`), so the closing card
shows "12" for that photo under "Most reacted." The user taps it. The pager opens that photo and
queries `photo_reactions`, which is empty, so the reaction bar shows nothing, contradicting the
number that led the user there. Separately, `photo_reactions` SELECT and `photo_comments`
INSERT are both gated by `is_roll_member` (`supabase/schema.sql:925-935, 1479-1484`), so a viewer
who is not a member of that specific roll gets a silently empty view, and typing a comment on a
stranger's chapter photo silently fails to persist. Any like or comment made from inside a recap
is also misfiled into the roll-thread tables instead of the feed tables the stats query, so it
never shows up in next month's numbers either.

Severity: high.

## 2. A burst pairing patch is silently and permanently dropped on a generic upload failure

`Flim/Services/PhotoService.swift:339-346, 394-396, 484, 539-549`

`captureAndUpload` computes a `patchEarlier` obligation (photoId of an earlier frame, plus the
freshly minted shared burst group) whenever a fresh capture pairs with the prior one in the same
stream. That obligation is only ever applied in two places: the ordinary success path (line 484)
and the roll-developed personal-fallback path (line 596). The generic catch path at
lines 539-549, reached by an ordinary network error or any other non-23505, non-roll-developed
insert failure, deletes the just-uploaded storage object and calls `queueForRetry` without ever
calling `patchEarlierBurstGroup`.

Failure scenario: two frames are captured 1s apart into the same roll. Frame A inserts and lands
with `burst_group = NULL` (it's the first of the pair). Frame B's analysis mints a new group and
sets `patchEarlier = (A.photoId, newGroup)`, and B's own Storage upload succeeds, but B's row
INSERT then fails on an ordinary network blip. Control reaches the generic catch, which queues B
for retry but never patches A. When the queued retry later succeeds, `captureAndUpload` takes the
`pending != nil` branch (line 340-341), which unconditionally returns `patchEarlier: nil`. B ends
up permanently in the database with a burst group that has no sibling, and A stays ungrouped
forever. The comment at line 648-650 claims "a dropped UPDATE here leaves one frame temporarily
ungrouped, never a lost photograph," but once the retry path is taken the loss is permanent, not
temporary, and there is no code path that ever revisits it.

Severity: medium-high. No cross-account leak, no lost photo, but a silent and permanent defeat of
the burst-grouping feature under exactly the flaky-network conditions the retry queue exists to
handle.

## 3. A second push tap for the same roll can overwrite the wrong photo's comment intent

`Flim/Views/Rolls/RollDetailView.swift:759-775`

`openAwaitingPhotoIfReady` captures `photoId` from `awaitingPhotoId` at entry (line 760), then
polls up to 5s for the photo to arrive in `pagerPhotos`, and only after the poll reads
`awaitingPhotoComments` (line 769), a single piece of shared `@State` rather than something
captured together with `photoId` at the top of the function.

Failure scenario: the user taps a push for photo P1 with `comments: true` while the roll is
already open. P1 isn't in `pagerPhotos` yet, so the poll begins. Before it resolves, a second push
for the same roll, photo P2 with `comments: false`, is adopted (`onChange(of:
pendingPhotoIntent.wrappedValue)`, line 475-478, spawns a fresh `Task` for every adoption, it does
not cancel or wait for one already in flight). P2 is already present, so its call runs to
completion immediately, sets `awaitingPhotoComments = false`, and presents P2. When P1's poll
later succeeds, it reads the now-overwritten `awaitingPhotoComments` (false) instead of P1's own
`true`, then sets `selectedPhoto = P1`, silently swapping the photo the user is currently viewing
(P2) for P1, without the comment sheet the original P1 push asked for.

Severity: medium.

## 4. Burst grouping's 3-second window is measured against a timestamp taken after the previous shot's full pipeline

`Flim/Services/PhotoService.swift:159-184, 327`

`enqueueCapture` chains each capture onto the previous one (`await previous?.value`, line 162)
before grading (line 177) and finally calling `captureAndUpload` (line 183), which samples
`capturedAt = .now` at line 327, i.e. after the entire prior shot's grading, Storage upload, and
DB insert have finished, and after this shot's own grading.

Failure scenario: on a slow connection where one shot's upload and insert take 2 to 4 seconds, two
shutter presses 200ms apart end up with `capturedAt` values several seconds apart, dominated by
the previous shot's own pipeline latency rather than the true gap between presses. `BurstMembership.matches`'s
`delta <= timeWindow` (3s) then fails for a genuine, textbook burst pair, and the two frames are
never grouped, exactly under the poor-network conditions the feature is meant to handle.

Severity: medium. False-negative only: the feature silently under-triggers, it does not
mis-group unrelated frames.

## 5. "Play again" on a chapter's closing card replays from a stale index

`Flim/Views/Profile/ChapterRecapView.swift:370-377`

`onSelectPhoto` sets `selection = idx` for whichever stat-line photo was tapped (line 371-372).
`onPlayAgain` (line 375-377) presents the pager again without resetting `selection` to 0, unlike
the initial "Play the month" button which does reset it.

Failure scenario: open the recap, tap "Play the month" (`selection = 0`), close the pager, reach
the closing card, tap a stat line such as "Most reacted" (`selection` becomes, say, 7), view that
one photo, close the pager, then tap "Play again" on the closing card. The pager reopens with
`startIndex: selection` still 7, silently skipping the first seven photos of the month instead of
replaying from the start as the button's label promises.

Severity: medium.

## 6. A reveal shown mid-poll can conflict with a pending push-photo presentation

`Flim/Views/Rolls/RollDetailView.swift:760`

`openAwaitingPhotoIfReady` checks `!showReveal` only in its entry guard. `replayReveal()` can set
`showReveal = true` at any point during the up-to-5s poll loop. If that happens, the function
still unconditionally sets `selectedPhoto = photo` at the end, attempting to present a
`.fullScreenCover(item:)` for the photo while `.fullScreenCover(isPresented: $showReveal)` is
already presented, and the pending push intent is discarded either way since
`awaitingPhotoId`/`awaitingPhotoComments` are cleared unconditionally.

Severity: low. Narrow timing window, no data loss, at worst a conflicting presentation or a
silently dropped push destination.

## 7. Burst cover selection ties a measured zero sharpness score with an unmeasured one

`Flim/Services/BurstGrouping.swift:47-53`

`sharpest(in:)` is documented to rank a `nil` sharpness score (unmeasured) lowest, never tying
with a measured score. The implementation coalesces `nil` to `0` (`a.sharpness ?? 0`), so a frame
that is genuinely measured at exactly `0.0` (confirmed reachable, `BurstDetectorTests` has a case
for a flat image scoring zero) ties with an unmeasured sibling instead of ranking above it, and
the choice falls through to the arbitrary `takenAt`/`id` tie-break.

Severity: low. Requires a perfectly flat scene co-occurring with a Vision failure on a sibling
frame in the same burst.
