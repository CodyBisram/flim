## Medium

**Flim/Views/Feed/FeedView.swift:665-674** (`inviteReminder`), `NewAccountIntro.swift:132`
(`announcementToShow`'s `usageKnown` gate), `Flim/Views/Components/FirstVisitLine.swift:152`
(`InviteReminderLine`'s `onAppear`). `inviteReminder` decides whether the Spotlight announcement is
about to claim the top line by calling `announcementToShow(.spotlight, usageKnown:
feed.ownSpotlightEntryIsCurrent, ...)`, which returns nil whenever `usageKnown` is false.
`ownSpotlightEntryIsCurrent` only becomes true once `reload()`'s Spotlight read lands; `.task` at
FeedView.swift:378 awaits `refreshInviteQuota()` strictly before reaching `reload()`. An account
with unspent invites that has never put a frame up for Spotlight and has never seen the 1.6.0
Spotlight announcement therefore renders the invite reminder first, while Spotlight usage is still
unknown and `spotlightUp` reads false. `InviteReminderLine.onAppear` inserts the account into
`NewAccountIntro.shownThisLaunch`, after which `InviteReminder.shouldShow` returns true
unconditionally for the rest of the launch regardless of `otherTopLineShowing`
(`NewAccountIntro.swift:162`). When the Spotlight read then lands and `AnnouncementLine` becomes
eligible (`hasSeen(.spotlight)` false, `alreadyUsed` false), both lines render stacked at the top
of the feed at once, the exact case `inviteReminder`'s own doc comment says it waits out.

## Low

**Flim/Services/FeedService.swift:1514,1549,1560,1565** (`setTags`/`removeMyTag`'s unguarded
`markTagWrite` calls) vs **:1045** (`resetForAccountChange` clearing `tagWrittenAt`). Commit
eae64bb tonight clears `tagWrittenAt` on account change but does not guard `markTagWrite` with an
account epoch. `setTags`/`removeMyTag` call `markTagWrite(postId)` once before their awaits and
again after ("again once the rows have landed", :1548). If an account signs out mid-edit, the
reset clears `tagWrittenAt` but leaves `tagWriteClock` at N; the incoming account's next tag read
captures `readStartedAt = N`. The departing edit's trailing `markTagWrite` call then still lands
(its network calls are not cancelled by the reset) and writes `tagWrittenAt[postId] = N+1`, so
`tagWrittenAfter` reports true for the incoming account's read of that same post id and the read is
suppressed for one cycle. This is the same underlying defect as ledger row 2026-10-14
(FeedService.swift tag-write clock); tonight's fix narrows but does not close it, so the ledger row
stays open with this updated scenario.

**Flim/Services/FeedService.swift:356-359** (`noteReactionMadeElsewhere`) vs **:1697-1716**
(`reactToPost`'s `reactionWritesInFlight` bookkeeping) and **:1759-1774** (`refreshReactions`).
`refreshReactions` only skips overwriting `reactionsByPost[id]` for ids in `reactionWritesInFlight`,
which only `reactToPost` populates. `noteReactionMadeElsewhere`, called from
`MainTabView.swift:804` when a push's reaction button is tapped, writes directly into
`reactionsByPost` without adding the post id to that set. A `refreshReactions` poll already in
flight for a visible post when the user reacts from a notification banner will resolve afterward
and overwrite `reactionsByPost[postId]` with the pre-reaction snapshot, making the just-added heart
disappear from the bar until the next poll (8-20s later per the view's own refresh cadence). The
server-side reaction is unaffected; only the on-screen bar regresses.

**FlimTests/InviteReminderTests.swift:28-31** vs **FlimTests/NewAccountIntroTests.swift:29,94,114,135,203**.
Both suites mutate the process-global `NewAccountIntro.store` pointer and restore it via `defer`.
Swift Testing runs suites concurrently by default, so one suite's test can read/write
`NewAccountIntro`'s state through a store pointer another suite's `defer` has already swapped back,
producing an intermittent, order-dependent test failure unrelated to the code under test.
