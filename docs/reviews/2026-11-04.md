# Review notes for 2026-11-04

1. **medium**, Flim/V2/V2Darkroom.swift:59,87: deleting a kept photo through the new print viewer leaves the Darkroom's own list stale.
   `V2OwnPrintsView` takes an `onDelete` closure that defaults to a no-op (`V2OwnPrintsView.swift` declares `var onDelete: () -> Void = {}`). V2Kept.swift's own call site passes `onDelete: { Task { await reload() } }`, but both of V2Darkroom.swift's call sites (the routed single-photo cover at line 59 and the kept-row pager at line 87) omit it. Concrete scenario: a user taps a photo in the Darkroom's kept row, which sets `pagerStart` and opens `V2OwnPrintsView(prints: kept, start: start.index)` (no `onDelete`); they delete it (the print has no `rollId`, so Delete is offered and succeeds through `UndoCenter`). `afterDelete()` fires the default empty closure, so the Darkroom's own `kept` array and `keptCount` are never refreshed. Back on the Darkroom screen, the deleted photo still shows in the kept row and still counts in `keptCount`, until an unrelated trigger (pull-to-refresh, backgrounding/foregrounding, a new capture finishing) calls `reload()`.

2. **medium**, Flim/V2/V2RootView.swift:37-39 (also Flim/V2/V2DeskChoice.swift:42): the System desk's own chrome can still show the phone's old appearance after a background/foreground cycle.
   Tonight's 55101f0 is meant to make the System desk track the phone's own light/dark setting (`V2SystemScheme.current`), and `V2DeskEnvironment` (Flim/V2/V2Theme.swift) deliberately reads `@Environment(\.scenePhase)` so returning from the background forces a re-read. `V2RootView`'s own `palette` computed property (used directly for its `V2Desktop` background and `.foregroundStyle(palette.ink)`) calls the same `V2SystemScheme.current` but has no such dependency, it only recomputes when `sizeClass`, `deskRaw` or `stampRaw` change. Concrete scenario: desk is System, the app is backgrounded, the phone's appearance is switched (Settings or Control Center), the app is foregrounded again without rotating or switching places. `V2DeskEnvironment`'s scenePhase-driven re-render updates the environment palette for descendants, but `V2RootView.body` itself is not re-invoked, so the desktop background and top-level ink colour it set directly stay on the old scheme until some unrelated state change (switching `place`, rotating) forces a redraw, a visibly split appearance in the interim. `V2DeskChoice.swift:42` has the identical gap (no scenePhase or other dependency behind `V2SystemScheme.current`), though that screen is shown only once during onboarding.
