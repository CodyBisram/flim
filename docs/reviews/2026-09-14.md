# Review notes for Sep 14

Review of commits from the last 24 hours (8718170..f13f95b).

## 1. .github/workflows/nightly-numbers.yml:25-30 (paired with scripts/repair_renditions.py:123)

The nightly numbers workflow has no `continue-on-error` on the rendition-repair step, so an expected, permanent condition in that script silently stops the day's line from ever being committed.

Failure scenario: `repair_renditions.py` now ends with `sys.exit(1 if failed or no_master else 0)`. A `NO MASTER` row is deliberately left alone ("deleting a row is the owner's call" per the script's own comment) and is never cleared, and `failed` also increments on a single transient per-photo exception without stopping the loop. Either one makes the script exit 1. The workflow's "Rebuild missing renditions" step has no `if: always()` or `continue-on-error: true`, so GitHub Actions skips every later step in the job by default once a step fails, including "Commit the line," which is what pushes `docs/NUMBERS.md`. `docs/NUMBERS.md` was already rewritten on disk by the earlier "Read the numbers" step, but that write is local to the runner and is lost when the job ends without committing. Because a `NO MASTER` row is never deleted, this recurs every subsequent night once it happens once, permanently and silently breaking the nightly numbers line with no further evidence in the repo that anything is wrong. It is also invisible to the app's own alerting: `nightly_numbers.sh`'s "cron run failed" alert only watches `cron.job_run_details` (pg_cron), not this GitHub Actions job, so the owner is not paged the way the feature's own design promises.

Severity: high.

## 2. supabase/functions/send-social-push/index.ts:1209-1230

The comment-likes push to a comment's author skips the `postVisibleTo` gate that the structurally identical "also commented" thread-participant push (a few hundred lines above, at line 795) was just given, so it can deep-link to a post the recipient can no longer open.

Failure scenario: user A comments on user B's post while following B, then unfollows B. `post_visible_to(A, post, B)` now correctly returns false, so RLS refuses A's re-open of that post. If someone later likes A's comment, the comment-likes loop still calls `notify()` with a route of `{t:"post", id: postId, comments:true}`, unconditionally, with no equivalent to the "A participant who has since unfollowed the author can no longer open the thread, so they are not told it continued" check the thread-participant loop just above was given for exactly this staleness reason. A gets a push whose route now dead-ends against the new followers-only read policy. Not a cross-account content leak (the previewed text is A's own comment), but it is the same class of stale-audience defect this migration set out to close everywhere else in this file.

Severity: medium.
