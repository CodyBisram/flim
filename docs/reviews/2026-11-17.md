## 1. medium, Flim/Views/Feed/FeedView.swift:272-294 (`docksComments`/`dockedComments.onScreen`), :538-560 (`syncDockedComments`), Flim/Views/Feed/CommentsSheet.swift:606-615 (`EnvironmentValues.dockedComments`)

`FeedUnitCard.setOnScreen` calls reach `dockedComments.onScreen` only through the `\.dockedComments`
environment value, which `FeedView.body` injects only inside the `docksComments` branch
(`:280`); the folded branch (`:287`) renders `feedColumn` with no override, so cards there read the
key's `nil` default and every `dockedComments?.setOnScreen(...)` call is a silent no-op. Nothing
else writes or clears `onScreen`. This diff deliberately dropped the old `dockedComments.clear()`
on fold (commit doc at :536-537: "Folding keeps the target; reopening reconciles it against the

follows it (`onScreen == {"9","10","11"}`). Fold the Duo shut (`docksComments` goes false); nothing
clears or updates `onScreen` from here on, including further scrolling, since the folded cards
never see the environment value. Scroll to the top of the (now single-column) feed. Unfold: the
`onChange(of: docksComments, initial: true)` handler calls `syncDockedComments()`, which still sees
the stale `onScreen == {"9","10","11"}`; the target's `unitId` ("9") is still a member, so the
re-target branch at :543 is skipped, and the later membership check at :549-550 finds unit "9" still
in `units` and returns early. The docked column keeps showing unit 9's comments while the visible

comments cite as the reason the column now tracks on-screen state at all.

## 2. low, Flim/Views/Camera/CameraView.swift:1274-1281 (`captureDelivery`'s epoch-mismatch branch), Flim/Services/PhotoService.swift:149-174 (`beginInFlight`/`endInFlight`/`inFlightCaptureIds`), :1083-1104 (`restorePendingCaptures`), Flim/Services/CaptureQueueStore.swift:193-202 (`save`)

When a captured photo's delivery closure fires after the account that took it is no longer current,
it writes the shot to `CaptureQueueStore` directly (`Task { _ = await queueStore.save(pending, raw:
data) }`) without bracketing the write with `PhotoService.beginInFlight`/`endInFlight`, unlike every
other writer of the queue (`enqueueCapture` at :250/:312, :1204/:1207, :1550/:1551). `restorePendingCaptures(userId:)`
protects in-progress writes from its own `dropEmpty` prune only via `diskPlan.excluding(inFlightCaptureIds)`
(:1102), so a write this branch makes is invisible to that protection.

Failure scenario: signed in as A, the shutter fires; `AuthService.sessionLost()` (an expired or
revoked session, not necessarily a user action, `AuthService.swift:1009-1011`) runs before the
delegate's delivery closure executes, bumping `AccountEpoch` and setting `currentUser = nil`; A's
session is then restored (a token refresh landing moments later), bumping the epoch again and
calling `ContentView`'s `restorePendingCaptures(userId: A)`. The delivery closure's epoch check now
reads stale, so it takes the mismatch branch and calls `queueStore.save` for the same account A it
started with. `save` first writes a `.writing` manifest entry with no raw bytes yet; if
`restorePendingCaptures`'s concurrent scan reads the manifest in that window, `CaptureRecovery`
classifies the entry as `(stage: .writing, hasRaw: false, not processed)` and `plan.dropEmpty`
removes it, deleting the manifest row out from under `save`'s still-running bytes write. `save`'s
final step re-adds the `.saved` stage to a manifest that no longer has the entry removed by
`dropEmpty`'s only visible side effect (`queue.remove(id:)`), and the next launch's prune can clean
up the orphaned bytes file with no record pointing at it. The shot is dropped with no entry in the
retry UI and no error surfaced.
