## 1. `supabase/functions/send-one-shot-push/index.ts:129-131` (high)

A single failed read makes the one-shot "the founding hundred is full" push fire for real while
real seats remain, and the claim ledger then permanently blocks the true completion push.

`foundingSeatsLeft()` destructures only `count` from the Supabase count query, not `error`:
`const { count } = await supabase.from("users")...; return count === null ? 0 : Math.max(0, 100 -
count);`. On a failed or errored read, `count` is `null`, so the function returns `0` ("no seats
left"), which is exactly the value `foundingFullCohort()` (line 665-666) treats as "send now"
(`if (await foundingSeatsLeft() > 0) return [];`). This is the exact anti-pattern the same file's
`update16Cohort` (line 640-641) explicitly guards against with its own comment: "A failed read must
not read as nobody has updated and push everyone."

Failure scenario: `.github/workflows/founding-full.yml` invokes this endpoint with `send=true`
every 30 minutes, unattended, for the weeks until the 100th seat actually fills. One transient
Postgres timeout or network blip on the `users` head-count read sends "The founding hundred is
full." to up to 100 real people while seats are still open. Every recipient is now claimed in
`one_shot_push` (primary key `(campaign, user_id)`), so when the seat count genuinely reaches zero
later, those same people are silently skipped and the real completion moment never reaches them.

## 2. `supabase/migrations/2026-09-29_review_account_takes_no_seat.sql:606-628`, folded into `supabase/schema.sql:15305-15327` (medium)

The one-time renumbering shift is guarded and driven by a username regex, not the review account's
identity, so a real member who takes a matching handle triggers it again on the next schema reapply.

Both the `IF NOT EXISTS` guard and the `FOR r IN SELECT ...` loop select any row matching
`lower(username) ~ '^applereview[0-9]*$'` with a non-null `signup_ordinal`. `users.username` is
UNIQUE but not reserved: `GRANT UPDATE (username, ...)` is held by `authenticated`
(`schema.sql:1777`) and `AuthService.isValidUsername` accepts `applereview1`. This repo's own audit
already documents that a full `schema.sql` reapply is a real, recurring operational event (see
`docs/AUDIT_1_6_1_POLISH_2026-09-28.md`'s B-1 finding about the cron block).

Failure scenario: member #45 renames to `applereview1`. The owner later reapplies `schema.sql` (a
routine event per the audit above). The guard finds a numbered row matching the pattern again, so
the DO block NULLs #45's number and shifts every ordinal above it down by one a second time, while
the 79 `founding_100` badge rows already granted do not move, permanently desyncing the visible
numbers from who actually holds the badge.

## 3. `supabase/migrations/2026-09-29_review_account_takes_no_seat.sql:78`, folded into `supabase/schema.sql:14776` (medium)

A real signup can permanently and silently lose their Founding 100 member number by picking a
username that happens to match the review-account pattern.

`assign_signup_ordinal()` sets `NEW.signup_ordinal := NULL` for any INSERT whose lower-cased
username matches `^applereview[0-9]*$`, with no check that the row is actually the App Review
account. The client's own INSERT grant lets a new signup choose their own `username`
(`GRANT INSERT (id, email, username, invite_code, display_name) ON public.users TO authenticated`,
`schema.sql:1772`), and `lock_signup_ordinal_trigger` pins whatever `signup_ordinal` a row gets at
INSERT time forever, with no supported path back.

Failure scenario: a new user signs up choosing the username `applereview3`. Their `signup_ordinal`
is set to `NULL` and can never be changed. Their profile shows no member number, they can never
earn `founding_100`, and they occupy no counted seat, with no admin tool in this codebase to
reassign a `signup_ordinal` once inserted.

## 4. `web/admin.html:1653-1672` (`authorId`) (medium)

The Feedback/Bug Catcher award flow resolves the recipient by looking up a cached, mutable username
at tap time, so a badge can go to the wrong account.

`list_feedback` currently returns only a `username`, not a `user_id` (the migration that adds
`user_id`, `90b21ee`, is folded into `schema.sql` but not yet applied per its own comment). `award()`
shows a confirm dialog built from the cached `r.username`, then calls `authorId(r)`, which re-queries
`users` for whichever account currently holds that username at the moment of the tap, not at the
moment the feedback was loaded or sent.

Failure scenario: the owner opens the feedback dashboard, sees a bug report from `@bob`, and leaves
the tab open. `@bob` renames to `@bob2`; a different account claims the now-free `@bob` handle. The
owner returns and taps "Award Bug Catcher" on the still-open row for `@bob`; the confirm dialog says
"Give @bob the Bug Catcher badge?", and `grant_badge` awards it to the new `@bob`, not the person who
actually sent the feedback.

## 5. `.github/workflows/founding-full.yml:38-42` (medium)

A run where every send attempt fails leaves the campaign permanently and silently dead, with the
owner never told and the workflow never disabled.

`one_shot_push` claims are inserted before each send attempt (`index.ts:902-904`), and a claimed-but-
undelivered person is deliberately never retried (the file's own top comment: "one missed nudge
beats a second one"). But the workflow's self-disable and owner-notification are gated only on
`sent -gt 0` (line 38), computed from the response's `sent` field, which counts only successful
deliveries, not attempts.

Failure scenario: at the moment the hundredth seat fills, APNs credentials are misconfigured (or
every recipient has a stale token). The run claims and attempts all ~100 recipients, all fail,
`sent=0, failed=100`. The `if [ "$sent" -gt 0 ]` gate is false, so the workflow is never disabled and
the owner is never notified. Every later run recomputes an empty, fully-claimed cohort forever: the
one-time "founding hundred is full" moment has permanently and silently failed to reach anyone.

## 6. `supabase/schema.sql:14838-14855` (`_ratchet_badges`'s founding_100 predicate) and `founding_left` (e.g. `schema.sql:7932`, `13802`, `send-one-shot-push/index.ts:130`) (low)

The Founding 100 rank excludes any `hidden_from_discovery` account from the count, but the seat
counters and the founding-full push cohort key only on `signup_ordinal <= 100`, so hiding any
numbered (non-review) account desyncs the two.

This is the same mechanism already relied on to exclude the App Review account, generalized: the
badge ratchet's rank subquery is `WHERE NOT x.hidden_from_discovery AND x.signup_ordinal <=
u.signup_ordinal) <= 100`, while `founding_left` and `foundingFullCohort`'s eligibility both use a
plain `signup_ordinal <= 100` (with only a name check for `applereview`, not a `hidden_from_discovery`
check).

Failure scenario: the owner hides a numbered, non-review account from discovery by hand (the only
documented way `hidden_from_discovery` is set). The badge ratchet's rank calculation now skips that
account, so the 101st-numbered account earns `founding_100`, but `founding_left` and the
founding-full push cohort still cut off at `signup_ordinal <= 100` and never include that 101st
person, so the true hundredth founder never receives the completion push.

## 7. `Flim/Services/ReviewPrompt.swift:239-246,86` (low)

The tenth-post rating-prompt moment, already fixed for two posts landing together, can still be
permanently lost when three or more posts land close enough together.

`checkPostMilestone` is invoked from an unawaited, unserialized `Task` per post
(`FeedService.swift:1839-1843`), each independently reading `ownPostCount` from the server and then
calling `postMilestoneCrossed(previous:current:)`. `previous == nil` (first check ever for the
account) only accepts `current` in `10...11`. Three such tasks racing on the same account's first
few posts can all read `previous = nil` from `UserDefaults` before any of them writes back, and all
resolve `ownPostCount` to the same final total once every insert has landed.

Failure scenario: an account at 9 posts shares three frames in quick succession from the sort deck
(the deck's own comment at `SortDeckView.swift:704` acknowledges a second post can land within three
seconds of the first). All three `checkPostMilestone` calls resolve `current = 12` with `previous =
nil`; `(10...11).contains(12)` is false for all three, so the tenth-post ask never arms, and
`defaults.set(max(12, 0))` stores `12` as the baseline, permanently disqualifying `previous < 10`
from ever being true again for this account.
