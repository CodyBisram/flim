## 1. docs/sql/flim_reader_role.sql:12-15 — the new read-only role can't read the tables it's built for, and fails silently (high)

The script grants table-level `SELECT` (`grant select on all tables in schema public to
flim_reader`) but never `BYPASSRLS` and never adds `flim_reader` to `authenticated`. The role
connects as a plain Postgres login over the session pooler (per its own header comment and
docs/ROUTINES.md), never through PostgREST/GoTrue, so `auth.uid()` is `NULL` in that session.
Every table this role exists to serve is RLS-gated on `auth.uid()` or scoped `TO authenticated`:
`users` ("users: own row", "users: visible to co-members"), `roll_members` (both SELECT
policies), `follows` ("follows: readable by authenticated", scoped `TO authenticated` so the
policy does not apply to `flim_reader` at all), and `invite_campaigns` (RLS enabled with zero
policies, "No client access... read only by redeem_invite/invite_preview"). None of these error
for a session with no JWT context; they evaluate to false/empty and return zero rows.

Failure scenario: the Pi's receiver runs a plain `SELECT ... WHERE id = $1` as `flim_reader` to
answer an inviter or day-one lookup (docs/ROUTINES.md, docs/prompts/PI_ROUTINES_2026-09-21.md
item 3a), or the Monday memo's "What the database says" section queries `users`/`roll_members`/
`follows`/`invite_campaigns` (item 4). Every query succeeds with HTTP/SQL success and returns 0
rows for every id, with nothing logged as an error — it will read as "no invite tree" / "no
inviter found" for every user, not as "access is missing."

Not yet applied to production (this is a hand-run docs/sql/ script, not a migration), so nothing
is broken today, but as written it will not deliver what it's described to.

Severity: high

## 2. Flim/Services/FeedService.swift:151-164 — fetchMyPostedPhotoIds pages by row position, the exact pattern the file next to it warns against (medium)

`fetchMyPostedPhotoIds` (new tonight, added to fix the 1000-row `posts` cap silently dropping the
"shared to your page" badge) pages with `QueryBatch.allPages` over `.range(from:to:)` with no
`.order()` clause. Six lines above it, `FeedService.swift:63-70` documents exactly why that's
unsafe for `posts`: "`posts` has no uniqueness on `created_at` and is inserted into constantly, so
a page fetched by ROW POSITION silently drifts under concurrent writes... anchoring to the
last-loaded row's own place... rather than 'rows N through M'" is why every other `posts`
pagination in this file uses a keyset cursor instead.

Failure scenario: an account with more than 1000 posts (the only case where this pages at all)
opens the Darkroom while sharing another photo from a second device. Between the `.range(0,999)`
and `.range(1000,1999)` requests, an INSERT shifts row positions; with no `ORDER BY` the second
page's window has no guaranteed relationship to the first page's, and a row can be permanently
skipped across both pages. The missed `photo_id` never enters `myPostedPhotoIds`, so
`hasSharedPhoto(id)` wrongly returns `false` and that photo's "shared to your page" badge silently
fails to show until the next full, uninterrupted reload.

Severity: medium

## 3. supabase/functions/send-daily-digest/index.ts:455 — the new posts read doesn't fail closed on a paging error, unlike the client_versions read added the same commit (low)

`fetchAllPages` returns `{ rows, failed }`. The `client_versions` read added in this diff checks
`failed` and returns early ("client_versions read failed; no digests sent", line 446) rather than
risk treating an unreadable table as "nobody launched recently." The `recentPosts` read three
lines later (line 455) destructures only `rows` and checks `recentPosts.length === 0`, discarding
`failed`.

Failure scenario: the 48-hour posts window exceeds 1000 rows (already happened once, at 1808 rows
on 2026-09-02, per this file's own header comment) and a later page errors. The run proceeds with
a partial post set and silently omits every post past the failing page from every recipient's
digest that night, instead of failing closed the way the file's own newly-established
`client_versions` pattern would suggest. Not a double-send risk and not a regression (an error here
previously also produced an incomplete result), so low rather than medium.

Severity: low
