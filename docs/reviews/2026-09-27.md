Covers the 29 commits from 2026-09-26 03:38 to 2026-09-27 00:00 (5ea15fb through 2265246):

## 1. `supabase/migrations/2026-09-26_spotlight_shot_this_week.sql:58-62` (medium)

`put_up_for_spotlight` now requires a post's `created_at` week AND its photo's `taken_at` week to
both equal the current Spotlight week. A roll's reveal is delayed from capture (`reveal_at`
defaults to `created_at + 12 hours`, `supabase/schema.sql:575`), so a frame can only be posted
after it develops.

Failure scenario: a roll is created Sunday 18:00 New York, so its frames reveal Monday 06:00 (past
the Monday 04:00 Spotlight-week boundary). Frames shot Sunday 18:00-23:00 have `taken_at` in week
W. The earliest they can be posted is after the Monday 06:00 reveal, which falls in week W+1, so
`created_at`'s week is W+1. The put-up check requires `taken_at`'s week to equal `created_at`'s
week; W ≠ W+1, so the RPC raises `not_this_week` every time, in both weeks, forever. Any roll
whose frames span the ~12-hour window before Monday 04:00 NY (or one whose reveal was pushed later
via `set_roll_reveal_at`) has its frames permanently locked out of Spotlight. The client menu
agrees with the server (`Flim/Models/Spotlight.swift:367`, `SpotlightPostedAsk.shouldAsk`), so this
shows only as a permanently disabled "Only frames shot this week can go up," never an error.

## 2. `Flim/Views/Darkroom/SortDeckView.swift:107,280-283` (medium)

On the deck's last card, a failed "Put it up" answer hides its own error message.

Failure scenario: the last frame in the deck is swiped to publish, triggering the Spotlight ask.
The user taps "Put it up" (`putUpAsked`, line 273): `askPhoto` is cleared and `spotlightOutcomeWatched`
is set `true` before the network call. `commit(photo, .publish, ...)` fails (server error, dropped
connection); `commit` sets `publishError` and returns `nil`, and line 281 sets
`spotlightOutcomeWatched = false`. With `cards.isEmpty && loaded` already true and both `askPhoto`
and `spotlightOutcomeWatched` now `nil`/`false`, the view body's condition at line 107
(`askPhoto != nil || spotlightOutcomeWatched`) flips to its `else` branch, whose
`Color.clear.onAppear { closeDeck() }` dismisses the deck immediately — before the `publishError`
text, which only renders inside the branch just abandoned, is ever shown. The photo has already
left the sort queue (`markSorted`), no post exists, and the user sees nothing.

## 3. `Flim/Views/Feed/FeedUnitCard.swift:216-225` (medium)

A day card's pager can be silently remapped onto the wrong photograph after two membership changes.

Failure scenario: a card shows `[p1, p2, p3]`; the reader swipes to `p2` (`selection = 1`,
`shownPostId = p2` via the `onChange(of: selection)` handler at line 249). `p2` is deleted
(`deleteCurrent`); `newIds = [p1, p3]`. In the remap handler (line 216-225), `viewing = shownPostId
= p2`, `newIds.firstIndex(of: p2)` is `nil`, and `selection (1) >= newIds.count (2)` is false, so
neither branch fires: `selection` stays `1` (now showing `p3`) but `shownPostId` is never updated
off `p2`, since it is only written from the `selection` `onChange`, which did not run. A second
membership change on the same card (a pull-to-refresh inserting an earlier capture via
`completeStraddlingDays`) makes `newIds = [p0, p1, p3]`. `viewing` is still the stale `p2`; not
found; `1 >= 3` is false; `selection` stays `1` — but index 1 in the new array is `p1`, not `p3`.
The pager silently jumps from `p3` to `p1` with no swipe, tap, or reload indication of why.

## 4. `Flim/Services/PushDestination.swift:208-219` (medium)

The 30-minute lapse on a held notification tap never actually elapses for a tap that keeps failing.

Failure scenario: a device is on a network that reports connected but times out requests. A post
push is tapped at 09:00; its lookup fails and `PendingPushDestination.hold(_:)` is called, which
calls `store(_:)` (clearing `heldAtKey`) and then writes `now` (09:00) to `heldAtKey`. Every
subsequent foreground that retries the same tap (`HeldTapRetry`) fails the same way and calls
`hold(_:)` again, which resets `heldAtKey` to that retry's `now` instead of preserving the original
09:00 stamp. `heldTapLifetime` (30 minutes) therefore never counts down to zero for a
persistently-failing tap: it can keep yanking the user to the tab it names on every foreground
indefinitely, which is the exact regression commit `e940b6b` (earlier tonight) introduced the
lifetime to prevent.

## 5. `Flim/Views/Darkroom/SortDeckView.swift:505-512` (low)

The Spotlight ask's auto-skip timer is keyed only by photo id, not by which ask it belongs to.

Failure scenario: frame A is swiped to publish at t=0, showing the ask and scheduling an 8-second
timer (`if askPhoto?.id == photo.id`, checked at t=8). The reader taps Undo at t=1, clearing
`askPhoto`. Frame A is re-swiped to publish at t=2, showing a new ask for the same photo. At t=8,
the first timer's check still matches on `photo.id` and clears the second ask 6 seconds early
(and, if A is the last card, closes the deck at t=8 instead of the intended 10-second window).

## 6. `Flim/Models/FeedUnit.swift:190-194` (low)

`hasUnseen`, which replaced `loadedRemaining` in tonight's header-count removal, dropped the
7-day retention filter the old function applied.

Failure scenario: the app is open with a loaded post created 6 days 23 hours 50 minutes ago,
sitting below the caught-up seam, never scrolled to. At the 7-day mark it ages out of
`feed_unseen_count`'s server-side window, but `hasUnseen` (line 190) has no time filter of its own
and only checks `isSeen`, so any later `seenStore.marksVersion` bump re-lights the Feed tab dot off
that post even though the server no longer counts it and nothing on screen can mark it seen.

## 7. `Flim/Views/Feed/FeedUnitCard.swift:207,592-597` (low)

A day card's "N new" pill can keep counting shots that are no longer new after a tab switch.

Failure scenario: a 3-shot card is on screen and marked (`newThisLook = {p1,p2,p3}`, pill reads "3
new"). The reader switches to Camera; `isFrontmost` goes false, so `markingEnabled` goes false, but
`onScrollVisibilityChange` does not fire (the card's scroll position hasn't changed), so
`newThisLook` (only cleared in that handler's `!visible` branch) is never reset. Returning to Feed,
`markingEnabled` flips back to true, firing `maybeMarkReached()` — which only ever `formUnion`s new
unseen ids into `newThisLook` and never removes stale ones. The pill still reads "3 new" for shots
already marked seen, until the card scrolls off screen and back.

## 8. `supabase/schema.sql:11621-11697` (low)

The new shot-this-week rule is enforced only at put-up time, with no sweep of what is already
queued.

Failure scenario: an entry was created between Spotlight's server launch (2026-09-25) and this
migration (2026-09-26) for a photo shot before that week began. The migration comment states "a
frame already up this week is not touched," and `list_spotlight_queue` returns `post_created_at`
but never `taken_at`, so the owner reviewing the queue cannot tell this entry apart from a
compliant one and can still choose and publish it, bypassing the rule the migration just added.

## 9. `supabase/migrations/2026-09-26_spot26_cohort.sql:13-15` (low)

`valid_until` is computed as NY-date-plus-8 at midnight, an 8 calendar-day window from creation,
while the row's own `note` column says "seven days from posting." The code comment above it agrees
with the 8-day arithmetic ("through the end of the seventh day after it"), so the SQL and the note
text disagree on what the code actually grants; the practical effect is the unlimited-use code
stays valid one day longer than the note promises.
