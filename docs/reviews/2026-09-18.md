## 1. supabase/schema.sql:8311-8318 — BALI26 cohort insert breaks a fresh schema bootstrap (high)

The BALI26 insert, folded in from `supabase/migrations/2026-09-17_bali26_cohort.sql`, is a plain
`INSERT INTO public.invite_campaigns (...) VALUES ('BALI26', 'f43287d4-...', ...)` with the
owner's UUID hardcoded. `invite_campaigns.inviter_id` is `NOT NULL REFERENCES public.users(id) ON
DELETE CASCADE` (schema.sql:5992). The two prior cohort-code fold-ins in the same file, SEPT10
(schema.sql:6130-6138) and FLIMGO (schema.sql:6779-6784), are deliberately written as
`INSERT ... SELECT ... FROM public.users WHERE id = ...` so that a database with no users row
inserts nothing instead of erroring; SEPT10's own comment states the reason. BALI26 does not
follow that pattern.

Failure scenario: running `scripts/schema_bootstrap.sh` (or the schema-bootstrap CI workflow)
against a from-scratch database has no `users` rows yet, so this INSERT fails with "insert or
update on table invite_campaigns violates foreign key constraint
invite_campaigns_inviter_id_fkey", aborting the bootstrap. Confirmed by reproducing the
`invite_campaigns` table and FK in an isolated Postgres instance and running the literal
statement.

Severity: high

## 2. Flim/Views/Feed/PeopleYouKnowRow.swift:84-93, FeedView.swift:509-510 — new row shares the known LazyVStack re-fire bug (low)

`PeopleYouKnowRow` is placed as a direct, non-`ForEach` child of the feed's top-level
`LazyVStack` (FeedView.swift:495), the same container already flagged (OPEN.md, 2026-09-10) for
re-firing `onDisappear`/`onAppear` on `FirstVisitLine` when SwiftUI reclaims and re-renders a
child that scrolls out of the lazy window and back. `PeopleYouKnowRow` holds its own `@State
people`/`loaded` and re-runs its `.task` (lines 87-93) from scratch on such a rebuild.

Failure scenario: on a feed tall enough that `PeopleYouKnowRow` scrolls out of the lazy render
window, scrolling back to it triggers a fresh `loadFollowers`/`discoverSections` round trip and a
visible flash as the row disappears and reappears, rather than staying mounted for the session.

Severity: low

## 3. Flim/Views/Feed/PeopleYouKnowRow.swift:88 — task guard races the feed's own follow-count load (low)

`.task`'s guard reads `feed.followingIds.count < Self.followThreshold` at entry, but
`followingIds` is populated by `FeedView`'s own independent `.task`/`loadFeed()` call
(`FeedService.swift:866`), with no ordering guarantee between the two sibling `.task`s.

Failure scenario: on cold launch or an account switch, `followingIds` is still empty (reset at
`FeedService.swift:782`) when `PeopleYouKnowRow`'s guard runs, so a user who already follows three
or more people can pass the guard and briefly see three suggested people, until the real follow
count lands and `visible` flips to false.

Severity: low
