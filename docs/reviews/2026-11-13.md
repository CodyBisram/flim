## 1. high, Flim/Views/Rolls/RollsView.swift:225-241 (`dockedRoll`)

On the Duo's open display, landing on the Rolls tab with no roll explicitly chosen (`dockedRollId
== nil`, true on every first visit) silently docks and fully mounts a live `RollDetailView` for
`activeRoll ?? readyRolls.first ?? developedRolls.first`. That view's own `.task`
(`RollDetailView.swift:688-737`) runs its whole on-open pipeline against that defaulted roll:
`RollRevealViewModel.shouldAutoPresent` fires the full-screen reveal the instant a developed,
unwatched roll becomes the default, and the notification-permission ask / `RollDevelopAskSheet`
fire for a defaulted developing roll, both gated elsewhere in this same file on the roll actually
being opened by a tap.

Failure scenario: no roll open, one developed roll whose reveal has never been watched. Switch to
the Rolls tab on the Duo's open display: the reveal takes over the whole screen immediately, with
no tap on that roll. Swiping it away burns `dismissedThisLaunch`; watching it writes
`rollRevealSeen.<id>` and fires the camera-roll auto-save gate, all before the user chose this
roll. The same mount can also fire the bare system notification-permission dialog for a new
account on tab switch alone, which a 2026-09-09 incident (recorded in this same file's comments)
was explicitly fixed to require an actual roll open for.

## 2. high, Flim/Views/Darkroom/DarkroomView.swift:530-536 (`dockedStart`), reached via `openRequestedPhoto` (:1793-1816)

On the Duo's open display, opening a widget deep link or a push-routed photo for a frame outside
the loaded grid page silently docks the newest developed shot instead of the requested one, with
no indication anything went wrong.

`openRequestedPhoto` resolves the target by id via `photoService.lookUpPhoto` and assigns it to
`selectedPhoto` without inserting it into `vm.photos`/`renderOrderPhotos`. The phone path already
has a guard for exactly this case: `pager(for:)` (:1754-1765) pages the found photo alone when it
is absent from the loaded order, with a doc comment (:1748-1753) explaining that `firstIndex ?? 0`
would otherwise silently open the newest photo instead. `dockedStart` reintroduces that exact
fallback: `ordered.first(where: { $0.id == picked.id })` returns nil for a frame not in the
current grid page, and the function falls through to `ordered.first(where: \.isReady)`.

Failure scenario: open display, Darkroom tab, tap a widget's look-back tile for a frame from two
months ago (outside the 30-row first page). The docked right panel shows last night's newest shot
instead, with no error and nothing to tell the user this is the wrong photo.

## 3. medium, Flim/Views/Feed/FeedView.swift:288 (`syncDockedComments`) vs FeedUnitCard.swift:878-893 (`deleteCurrent`)

Deleting a post from a multi-post day on the Duo's open display can leave the docked comments
column open on the now-deleted post. `syncDockedComments` only re-runs when `units.map(\.id)`
changes (:536), and a `FeedUnit`'s id is `"\(author.id)|\(dayKey)"`
(`Flim/Models/FeedUnit.swift:22`), so deleting one post out of several on the same day leaves the
unit id list unchanged and the sync never fires. `deleteCurrent` removes the post from `feed.feed`
immediately; the card's items-remap leaves `selection` pointing at whatever index now fills that
slot, so `onChange(of: selection)` doesn't catch it either.

Failure scenario: open display, a card with three of your own shots from the same day, docked
column showing shot 2's comments. Delete shot 2. The card advances, but the right column keeps
rendering shot 2's now-dead thread and a reply typed there posts a comment against a deleted
post id.

## 4. medium, Flim/Views/Darkroom/DarkroomView.swift:554 (docked pager `.id`) with `viewingID` at :911

The docked pager's identity is keyed on `dockedStart.id`, not on what it is currently showing, so
a background develop-poll refresh can silently rebuild the pager back to the default start while
the user has swiped elsewhere, and the grid's selection ring is then left pointing at the wrong
frame (`:911`, `viewingID ?? dockedStart?.id`, goes stale the moment the rebuild drops it).
`onShow` only updates `viewingID` from `onChange(of: selection)` (`PhotoPagerView.swift:602-608`),
never on mount, so the pre-rebuild value survives the teardown and no longer matches what's on
screen.

Failure scenario: open display, Darkroom tab, swipe the docked viewer a few frames past the
default start. A developing frame in the grid finishes during the 60s poll and becomes the new
`isReady` default; `dockedStart.id` changes, the `.id(...)` string changes, SwiftUI tears down and
rebuilds the pager at the new default start, and a comment being typed in that pager's comments
sheet at that moment is lost with the rebuild. The grid keeps its ring on the frame the user had
swiped to, which the docked viewer no longer shows.

## 5. low, Flim/Views/Components/PhotoPagerView.swift:526 (`.undoCapsuleHost(bottomPadding: 44)`)

The docked pager hosts its own undo capsule unconditionally, with no `docked` guard, even though
`MainTabView.swift:501` already hosts one over the whole docked layout. `UndoCapsule.swift:8-11`
states the invariant this depends on: only one host is ever visible because a `fullScreenCover`
paints over the tab host. In the docked Darkroom the pager is inline, not a `fullScreenCover`, so
both hosts are mounted and visible at once. `CommentsSheet` already handles this correctly, its
`docked` branch (`CommentsSheet.swift:81-87`) omits the host entirely, `PhotoPagerView` does not.

Failure scenario: open display, Darkroom tab, stage a delete from the docked viewer. Two undo
countdown capsules render at once: one inside the right panel, one above the tab rail.
