## 1. Flim/Views/Rolls/RollCarouselView.swift:259, 284-299 — reaction revert can corrupt the next photo's reaction state (medium)

`toggleReaction` optimistically mutates the single `@State private var reactions: [PhotoReaction]`
(line 21), then hands `OptimisticToggle.shared.perform` a revert closure that also mutates
`reactions` directly (lines 291-293, 296-298). `reactions` is not keyed by photo id: `loadAround`
resets it to `[]` and refetches it fresh every time `selection` changes (line 259, driven by
`.task(id: selection)` at line 127). `PhotoPagerView.swift` and `RollRevealViewModel.swift` made
the equivalent change the same night by keying their dictionaries on photo id
(`reactionsByPhoto[photo.id]`) specifically so a revert always lands on the right photo's slot
(PhotoPagerView.swift:1095, RollRevealViewModel.swift:379); `RollCarouselView` adopted
`OptimisticToggle` but not the keyed storage.

Failure scenario: viewing photo A in the carousel, tap a reaction (optimistically applied to
`reactions`), then swipe to photo B before the write resolves. `loadAround` clears `reactions` and
loads B's reactions. If A's write then fails (network drop, or a non-duplicate server error),
`OptimisticToggle`'s revert fires against whatever `reactions` holds now — B's data — either
removing a reaction B actually has (same emoji, e.g. the same user reacted the same way to both
photos) or appending a phantom `PhotoReaction(photoId: A's id, ...)` into what the view renders as
B's reaction bar. The corruption is visible until the user swipes away and back, which forces a
fresh `fetchReactions` call.

Severity: medium

## 2. Flim/Models/Roll.swift:117-121 — a new roll's suggested name ignores the app's 4am day boundary (low)

`Roll.defaultName(on:calendar:locale:)` formats `date` (called with `.now` from
`CreateRollView.swift`'s `.onAppear`, line 52) straight through `DateFormatter`, using the raw
calendar day. `FeedUnit.dayKey` (`Flim/Models/FeedUnit.swift:29-37`) exists precisely because "a
genuine 02:00 shot files under yesterday, which is what the person who took it would call it";
`defaultName` does not apply that same shift. This is the same class of bug already open against
`RollDevelopAskSheet.swift:30` (OPEN.md, 2026-09-10), now in a second, different call site added
tonight.

Failure scenario: a group creates a roll for their Saturday-night outing at, say, 1:30am. Calendar
day has already turned over to Sunday, so the prefilled name reads "Sunday, Sep 21" instead of
"Saturday, Sep 20" — the night the roll actually documents, and the label the Feed's own dayKey
grouping would use for photos taken in that same window. Cosmetic only (the name is freely
editable before the roll is created), which is why this is low rather than medium.

Severity: low
