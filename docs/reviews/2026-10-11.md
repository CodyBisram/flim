## 1. supabase/functions/send-daily-digest/index.ts:533-538 (medium)

The run-budget break still assumes an hourly cron ("the next hour's tick finishes the rest"),
but the same commit (8756519) moved the job's production schedule to once a day (`0 16 * * *`).

Failure scenario: `tokensByUser` is built from `device_tokens` read ordered by `token` ascending
(:416-418), so the `for (const [userId, tokens] of tokensByUser)` iteration order at :537 is
deterministic across runs. Once the candidate set makes a run exceed `RUN_BUDGET_MS = 200_000`,
the loop breaks (:538) at the same point in that deterministic order every day. `digest_state` is
only written for users actually reached (not the tail that got cut), so that same tail of
accounts is skipped again on the next day's run. Under the old hourly schedule the next tick
(still inside `DIGEST_INTERVAL_HOURS`) picked up the skipped tail later the same day; under the
new once-daily schedule that tail never receives a digest at all, for as long as the run keeps
hitting budget.

## 2. Flim/Services/PhotoService.swift:1556 (medium)

`deletedPhotoIds.contains(...)` is checked once at the `retryFailedUploads` call site (:1556),
before `captureAndUpload` (:1560) runs its own Storage upload, burst analysis, and row insert
(:678-684), none of which re-checks `deletedPhotoIds`.

Failure scenario: photo P's upload previously landed server-side but the client never saw
confirmation, so P sits in both the Darkroom and `failedUploads`. `retryFailedUploads` runs;
`confirmedUploaded` times out on a flaky connection, so P lands in `stillPending` with
`deletedPhotoIds` still empty, and `captureAndUpload(imageData:...)` begins its Storage upload
for P. While that upload (and the concurrent burst analysis awaited before the insert) is still
in flight, the user deletes P from the Darkroom; `deletePhoto` adds P's id to `deletedPhotoIds`
(:1910) and clears its persisted copies. `captureAndUpload`'s own insert at :678-684 then
proceeds anyway and recreates P's row (the 23505 self-heal at :685 doesn't help, since the row
was actually deleted), reinserting a photo the user just deleted back into the roll for every
member. This is exactly the resurrection the code's own "audit DS-1" comments at :1546 and :1555
say this guard exists to prevent; the guard just runs too early to close the window.

## 3. supabase/schema.sql:9520 vs supabase/functions/send-daily-digest/index.ts and docs/ROUTINES.md:27 (low)

`schema.sql`'s `cron.schedule('flim-daily-digest', '0 14-23,0-1 * * *', ...)` (:9519-9520, guarded
by `IF NOT EXISTS`) was not updated when the job's documented production schedule changed to
`0 16 * * *` (commit 8756519). `docs/ROUTINES.md:27` likewise still reads "hourly 10:00 to
21:00". No migration in `supabase/migrations/` changes the `flim-daily-digest` cron entry to
match. The `IF NOT EXISTS` guard means this cannot silently revert an already-running production
job, but a fresh bootstrap of the database from `schema.sql` (disaster recovery, a new
environment, `schema-bootstrap.yml`) would schedule the job on the old hourly cadence, silently
undoing the owner's 2026-10-10 decision with nothing in the repo disagreeing.
