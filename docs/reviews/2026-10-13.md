## high: the two pending digest migrations undo each other's schedule change when applied in filename order

`supabase/migrations/2026-10-12_digest_hourly.sql` (whole file) and
`supabase/migrations/2026-10-12_ops_ledger_fixes.sql:38-42` both carry the header "NOT YET
APPLIED. The owner applies it" and both end with a `cron.alter_job` on `flim-daily-digest`:
`digest_hourly` sets the schedule to `'0 * * * *'` (hourly, required by tonight's
`send-daily-digest` rewrite, which now sends each person their digest only when its own run
happens to land on that person's local noon); `ops_ledger_fixes` sets it to `'0 16 * * *'`
(once a day at 16:00 UTC, the schedule production had *before* tonight's change, per its own
comment: "production has run once a day at 16:00 UTC since 2026-10-10... applying it there
changes nothing").

That "changes nothing" claim assumes `ops_ledger_fixes` runs before `digest_hourly`. Migration
tools apply pending files in filename order, and this repo already has same-day migrations
disambiguated purely by name (e.g. three `2026-09-25_*.sql` files, four `2026-09-29_*.sql`
files). Lexicographically `"2026-10-12_digest_hourly.sql"` sorts before
`"2026-10-12_ops_ledger_fixes.sql"` (`d` < `o`), so a normal `supabase db push` applies
`digest_hourly` first (schedule -> hourly) and `ops_ledger_fixes` second (schedule -> back to
once daily at 16:00 UTC). The final state is the pre-10-12 once-a-day schedule, not the hourly
one the new `send-daily-digest` code requires.

`supabase/schema.sql` folds both blocks in the opposite, correct order (ops_ledger_fixes' alter
at :17684 runs before digest_hourly's alter at :17700, leaving a fresh bootstrap at hourly), so
only the live migration path is affected, not a fresh database. But the live migration path is
exactly what the owner runs to ship tonight's feature.

Failure scenario: the owner deploys the new `send-daily-digest` function and runs the two
pending migrations in the normal way (`supabase db push`, filename order). The cron job ends up
on `'0 16 * * *'` instead of `'0 * * * *'`. `send-daily-digest` now only ever fires once a day,
at 16:00 UTC. Its new per-recipient noon filter (`localHour(zone, runAt) !== SEND_LOCAL_HOUR`)
passes only for users whose local noon falls at 16:00 UTC (UTC-4, e.g. US Eastern during EDT);
everyone else's `tokensByUser` entry is deleted every single run and they never receive a daily
digest again, with no error, timeout, or log line distinguishing this from working-as-intended
(`"nobody's noon this hour"` is a normal 200 response).
