# Review notes, 2026-09-12

Scope: commits from the last 24 hours on main (f220241 through da1dd39).

## 1. Flim/Services/RollService.swift:27, :111

Defect: `resetForAccountChange()` never clears `followUpInvites`, contradicting the property's own doc comment ("cleared with the rest on account change"), so a departing account's follow-up roll invites survive into the next signed-in account's session.

Failure scenario: account A has a pending follow-up roll invite showing on the Rolls tab. The user signs out and signs into account B on the same device. `ContentView` calls `rolls.resetForAccountChange()`, which clears `rolls`, `memberCounts`, and `coverPaths` but leaves `followUpInvites` populated with A's invite `Roll`. `RollsView` renders that stale card for B on the first frame, before `fetchFollowUpInvites()` returns (and it silently keeps the stale value if that RPC fails at all, by design). B can tap Join on the leftover card, which calls `rolls.joinRoll(inviteCode:)` with A's invite code, enrolling account B into a roll meant for account A.

Severity: high

## 2. supabase/functions/send-social-push/index.ts:272, 300-322, 729-772, 1048-1076

Defect: `pendingRetry` is a single `Set<string>` keyed only by `sourceKey`, not by `(sourceKey, recipient)`, but both the comment-notification block and the roll-photo-comment block call `notify()` once per recipient with the same shared `sourceKey` for that one comment or photo-comment batch, so whichever recipient is processed last decides whether the source row is marked `push_sent`, and one recipient's success (or no-device-token pass) can erase another recipient's still-pending failure.

Failure scenario: user C comments on user O's post. O's push send fails (a transient APNs error), which records a `push_deliveries` row with `delivered:false` and adds `comment:<id>` to `pendingRetry`. The loop then reaches a mentioned user or thread participant with no registered device token, which counts as `delivered = true` per the `sent > 0 || tokens.length === 0` rule at line 314, and that call deletes `comment:<id>` from `pendingRetry`. `settled("comment:<id>")` now returns true, so `post_comments.push_sent` is set true. O's failed delivery is never looked at again: the query that finds unsent rows only selects `push_sent = false`, so the post owner permanently never receives the notification for that comment. The identical pattern applies to the roll-photo-comment thread block.

Severity: high

## 3. Flim/Services/PhotoService.swift:1262, 1285, 1398

Defect: `retryFailedUploads()` and `restoreFailedUploads()` remove a confirmed-already-uploaded record from `failedUploadStore` only, instead of going through `clearPersistedCopies(photoId:userId:)`, so the matching `CaptureQueueStore` manifest entry is left behind at stage `.processed` with `hasRaw == true`.

Failure scenario: a capture's storage upload and row insert both succeed server-side, but the client is killed before it sees the response. On the next launch, `restorePendingCaptures` queues the shot into `retryFailedUploads`, which finds it already `confirmedUploaded` and removes only the `FailedUploadStore` copy, leaving the manifest entry as `(.processed, hasRaw: true)` with the id no longer in `processedIds`. On the following launch, `CaptureRecovery.plan` matches `(.processed, true, false)` and replays the raw capture, so a photo that is already fully uploaded gets fully re-graded and re-uploaded. This is self-healing only because the resulting duplicate insert eventually hits the 23505 path in `captureAndUpload`, which finally calls `clearPersistedCopies`.

Severity: medium
