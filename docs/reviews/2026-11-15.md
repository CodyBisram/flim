## 1. high, supabase/release-1.7/01_month_boxes.sql:17-28 (`post_visible_to`'s `put_away` rule), bypassed by supabase/schema.sql:11234-11251 (`spotlight_post_public`) and :13204-13244 (`_spotlight_weeks_for`)

A post the owner puts away stays visible to every signed-in user through the Spotlight read path.
`post_visible_to` is the only place `put_away` is checked, but the posts SELECT policy and the
`storage.objects` read policy (schema.sql:11266-11287) are `post_visible_to(...) OR
spotlight_post_public(...)`, and `spotlight_post_public` never reads `put_away`: it only requires
`chosen_at IS NOT NULL` and the week published. `_spotlight_weeks_for`, the function behind the
Spotlight strip and a user's own page shelf, filters `hidden`, blocks, and `covered_post_visible`
but not `put_away` either.

Failure scenario: a post was chosen and published in a Spotlight week, then the owner opens that
month's box and puts the shot away (`ChapterRecapView.swift:244` tells them "Put-away shots stay
yours"). Any authenticated user who is not a friend, never followed the owner, and is not tagged
can still `GET` the post row and the signed storage object through the spotlight disjunct, and
still sees it on the Spotlight strip and on the owner's own page shelf.

## 2. high, Flim/Views/Profile/ChapterRecapView.swift:482-487 (load), :339 (Edit button), :498 (sheet's captured set), :260-262 (applyBoxEdit's diff)

Opening the box Edit sheet before its put-away read has landed silently un-hides every shot the
owner had put away in that month, and separately can overwrite a chosen cover with the month's
default.

`chapters.putAwayPostIds` only becomes accurate after `.task(id: viewModel.monthPhotos.count)`
finishes a full extra round trip (`await viewModel.signMonthThumbs(feed: feed)`), but the Edit
button renders as soon as `!viewModel.monthPhotos.isEmpty`, well before that. `MonthBoxEditView`
captures `putAway` into `@State` at init from whatever `chapters.putAwayPostIds` holds at that
instant, and `applyBoxEdit` treats that captured set as complete truth: `before =
monthPhotos.filter { putAwayPostIds.contains }`, `toBack = before.subtracting(putAway)`, and every
id in `toBack` gets `setPutAway(false, ...)`.

Failure scenario: a month with two shots already put away. Open the recap and tap Edit the instant
it appears (before the put-away read resolves), then tap Done without touching anything. The sheet
captured `putAway = []`; by the time Done fires, `before` correctly resolves to both ids, so
`toBack` is both ids, and `setPutAway(false, ...)` runs for both, un-hiding shots the owner
deliberately hid, with no confirmation and no notice. The same stale-capture pattern applies to the
sheet's `cover` field: an early-open Edit hands back the month's default cover and overwrites
whatever cover the owner had actually chosen.

## 3. high, Flim/Services/DarkroomLibrary.swift:173 (`fetchMonth`), :184 (`ensureMonth`), :300 (`replacingMonth`), :309 (`monthsToRefetch`)

The on-device Darkroom library buckets a photo's month from its raw `takenAt` via
`DarkroomYearMonth(date:)` (`Flim/Models/DarkroomYearMonth.swift:16-20`, plain
`calendar.dateComponents([.year, .month], from: date)`), while the server's
`darkroom_month_summary_v2` and this same file's own `fetchMonth` cursor
(`DarkroomYearMonth.upperEdge()`, which explicitly adds `FeedUnit.dayBoundaryHour`) both bucket by
the app's 4am day boundary. A shot taken between midnight and 4am on the 1st of a month is "last
night" by every other bucketing site in the app but lands in the new month here.

Failure scenario: one shot taken 2026-11-01 at 02:00 local, in an October with more than one
page's worth of kept shots. `monthsToRefetch` disagrees with the server on both October's and
November's counts on every sync, so it never converges and keeps re-fetching both months on every
Darkroom open. Worse, `fetchMonth(October)` seeds its cursor at November 1 04:00, so the 02:00
shot is the first row returned; it fails the `DarkroomYearMonth(date:) == month` filter, which
trips the "ran past the month's start" break after a single page. `replacingMonth` then deletes
every row of October past that page from the on-device library and the saved file, including rows
the server still has, with no mechanism that ever brings them back short of a reinstall.

## 4. medium, Flim/Views/Feed/UserPageView.swift:299-302 (`gridPosts`) and :1293 (`taggedInPostIds` fetch gate)

The page header pill and the locked empty state were switched this diff to the 1.7 mutual-friend
test (`isFollowing && followsMe`), but `gridPosts` and the `taggedInPostIds` fetch were left on the
old one-way `isFollowing` test, so the two disagree for exactly the relationship 1.7 introduces: a
pending, not-yet-reciprocated follow.

Failure scenario: you follow someone who has a post with a chosen, published Spotlight frame but
has not added you back. `fetchUserPosts` returns that post (the spotlight RLS disjunct lets it
through regardless of follow state); `gridPosts` sees `isFollowing == true` and returns every post
unfiltered, so the chosen frame renders a second time in the grid directly under the Spotlight
shelf, and the locked note ("Requested. You'll see the rest...") never shows because `pagePosts`
takes the non-empty branch. The page reads as already unlocked when it is still pending.

## 5. medium, supabase/release-1.7/01_month_boxes.sql:63-71 (`month_box_covers`)

`month_box_covers` filters its lateral post lookup only on `NOT p.hidden`, omitting
`covered_post_visible`, the gate every other post read in this schema carries
(the posts policy, the storage policy, `profile_chapters`, `chapter_photos`, and
`_spotlight_weeks_for` all apply it).

Failure scenario: the owner has an active row in `covered_post_windows` and the month's chosen
cover photo belongs to a post made inside that window, making it covered (invisible to everyone
but the owner and themselves while covered). A friend with no covered window of their own calls
`month_box_covers`; `post_visible_to` alone is true on the mutual follow, so the RPC hands them the
covered post's `thumb_path` and stores it as the chosen cover, but the storage policy still
refuses the object, so the friend's view of that month's box renders blank, and the covered post's
storage path (deliberately withheld elsewhere) has been disclosed to a client the owner can't see.

## 6. medium, supabase/functions/send-social-push/index.ts:496 (with the ledger key at :1550 and the unconditional mark at :1588-1592)

`push_deliveries` rows are never purged, so once a `follow:<A>:<B>` row is marked `delivered`, any
later follow of B by A after an unfollow is silently recorded `push_sent = true` with no push sent,
and no mechanism ages the row out. This mechanism predates tonight's diff, but tonight's flip of
`FRIENDS_MUTUAL` to production (index.ts:61-66) is what makes it load-bearing: under mutual
friends, a push is the only signal that a friend request exists, and cancel-then-re-request is a
normal interaction on the new friends chip (the client side of this exact chip is 2026-11-12's open
rows 141-142 in this ledger).

Failure scenario: A requests B, B is pushed and declines/doesn't act, the request is cancelled
(a hard delete of the `follows` row with no ledger cleanup), and A requests B again weeks later.
The fresh `follows` row polls with `push_sent = false`, `notify()` finds the old `delivered` ledger
entry for the same `(A,B)` key and returns 0 without sending, and the poller marks `push_sent =
true` regardless. B is never told a second request exists.

## 7. low, supabase/schema.sql:7546-7557 (`can_see_posts_of`) vs supabase/release-1.7/02_mutual_friends.sql:12-24

`schema.sql` still carries the one-way `can_see_posts_of` definition; the mutual-friends
redefinition in `02_mutual_friends.sql` is not folded into it anywhere. This is correct today
(02 is deliberately held back until `minimum_version` reaches 1.7), but the moment it is applied to
production, a fresh bootstrap built from `schema.sql` alone will grant post visibility on a one-way
follow while production requires mutual, and nothing in `release.test.sql` would catch the drift
since it explicitly sources 02 itself.

## 8. low, supabase/release-1.7/01_month_boxes.sql:63-67 (`month_box_covers`'s lateral)

The lateral picks the cover photo's newest post by `ORDER BY p.created_at DESC LIMIT 1` filtering
only `NOT p.hidden`, and applies `post_visible_to` (which carries the `put_away` test) only after
that row is already chosen. `public.posts` has no unique constraint on `photo_id`, so one user can
hold two posts of the same photo. If the newest post of the cover photo is put away and an older
one of the same photo is not, the lateral still returns the put-away one, `post_visible_to` fails
it, and the chosen cover silently vanishes for friends even though a friend-visible post of that
exact photo exists.

## 9. low, supabase/functions/send-social-push/index.ts:1577-1580

The "@X added you back" vs "@X asked to be friends" choice is read from the live follow graph at
push-send time, not at the time the triggering follow happened, so a recipient who accepts before
their own push goes out gets told the wrong direction.

Failure scenario: A requests B; B, already in the app, taps "Add back" before the cron's next poll
picks up A's row. When it does, the back-read at send time sees B now follows A and pushes B
"@A added you back", but B is the one who added back; A asked first. The reverse push to A is
worded correctly.

## 10. low, supabase/functions/send-social-push/index.ts:1582-1585

The `IS_V2` "asked to be friends" push passes no `category`, so it carries no action button, while
the invite-join push two cases above it (:1562) does pass `FOLLOW_BACK_CATEGORY`. The "Add them
back" action button (renamed for 1.7 in the same commit, `NotificationActions.swift:40-46`) never
appears on an ordinary friend request's push, the one push that most wants it.

## 11. low, Flim/Views/Profile/ChapterRecapView.swift:597-609 (`heldId`)

`heldId` is set by the long-press that stages a cover/put-away choice and is only ever cleared by a
tap on the same tile. A hold that ends with a scroll (long-press fires, then the touch drags to
scroll the grid, cancelling the tap) leaves `heldId` set with no tap to clear it, so the next
single tap on that same tile is consumed by the stale-clear branch instead of registering.

## 12. low, Flim/Views/Desk.swift:93 (`preferredColorScheme`) with :99-104 (`DeskSystemScheme.current`)

A desk set to "Match system" stopped tracking the system appearance live: this diff replaced a
plain `nil` (which lets SwiftUI follow the system scheme continuously) with an explicitly resolved
scheme that only recomputes on `deskRaw` or `scenePhase` changes. Left frontmost across an
automatic light/dark switch (e.g. sunset with Automatic appearance), the whole app stays on its old
scheme until backgrounded and reopened.
