# Review notes for 2026-10-14

Reviewing the combined diff of commits 9ec0bc5, 58475c4, 770fa00, 7ea9052, 9522cb9 (the last 24
hours on main): the invite-push feature, the Spotlight-presence UI work, and a large batch of
fixes for previously-open findings (tracked separately in OPEN.md).

## Medium

**supabase/functions/send-social-push/index.ts:285-311**, `inviteJoin`'s own comment claims "A
cohort or roll code names no person and never matches," but `redeem_invite` writes the identical
`invited_by:<uuid>` note format for a cohort campaign (`supabase/schema.sql:6866`,
`inviter_id` = the owner's own account for BALI26/SEPT10/FLIMGO) and for a roll code
(`supabase/schema.sql:6884`, the roll's creator) as it does for a personal code. Every cohort
signup's first-run follow of its campaign owner (`UsernameView.swift:182-185`) lands inside
`INVITE_JOIN_WINDOW_MS` of signup and matches `invited_by:<owner>` exactly, so the owner receives
"@x joined FLIM with your invite" with a Follow-back button for every cohort-campaign signup, not
only for an actual personal invite. Same for any roll creator whose roll code admitted someone who
then follows them within 72h. The gate the comment describes does not exist in code.

**Flim/Views/Feed/SpotlightViews.swift:321,381-394 (SpotlightClosingHost), Flim/Services/FeedService+Spotlight.swift:434**, 
`SpotlightClosingHost.load()` never calls `refreshOwnSpotlightEntry()`; it only reads the cached
`feed.currentSpotlightEntry`. Ordinary foregrounding does not refresh that cache
(`FeedView.swift:431-435`), only a full feed reload or the 4am boundary does. A user puts a frame
up from a second device; their phone's feed, not reloaded since, still shows the closing row
offering "Put one up" with the old (stale) entry. Tapping it calls `putUpFromSessionSheet`, whose
own freshness re-check (`FeedService+Spotlight.swift:434`) compares the offer's `shownSwap`
against that SAME stale cached entry the offer was itself built from, so the two always agree and
the re-check never fires. `put_up_for_spotlight` goes ahead and replaces the frame put up from the
other device, with no swap warning ever shown, the person only learns from the after-the-fact
"Your frame from Friday came down" notice. This is the exact mechanism OPEN.md's 2026-09-28 row
describes for `SortDeckView`, now present in `SpotlightClosingHost`, which did not get the same
"re-read on every open" fix.

**Flim/Services/RemotePush.swift:203-234 (detachAfterSessionLoss, retrySessionLossDetach)**, both
functions write `state.sessionLossDetach` unconditionally, with no chaining or single-flighting
against whatever task is already in that slot. `pendingSessionLossDetachKey` is set after a failed
detach (plausible exactly because the network is bad). `retrySessionLossDetach()` runs on launch
and on every foreground while signed out (`ContentView.swift:272,298`); two foreground events close
together (e.g. checking a Wi-Fi toggle and coming back) each create a new detach task and overwrite
the slot, orphaning the earlier one while it is still on the wire. If the user then signs in,
`claim()` awaits only the current (later) task; if the orphaned earlier task later succeeds, it
calls `detach_device_token`, which deletes `device_tokens` by token alone
(`supabase/schema.sql:4174-4188`, no account check), removing the row the fresh sign-in's
`register_device_token` just wrote. `registeredAccountId` stays set client-side, but the server
has no row, so `NotificationService.shouldScheduleLocalReminder` reads `isTokenRegistered == true`
and skips the local fallback too: the newly signed-in account gets neither remote nor local develop
pushes until the next successful claim.

**Flim/Views/Feed/SpotlightViews.swift:309-394 (SpotlightClosingHost), Flim/Views/Feed/FeedView.swift:689**, 
`SpotlightClosingHost` sits as a direct child of the feed's top-level `LazyVStack`, the same
position class as `FirstVisitLine` (OPEN.md 2026-09-10) and `PeopleYouKnowRow` (OPEN.md
2026-09-18), both already documented in this file as losing their `@State` and re-running `.task`
when scrolled out of the lazy stack's realized range. `session`/`prepared` are `@State` here too:
scrolling the closing row four screens down the feed and back destroys and rebuilds the host,
re-issuing `load()`'s three serial reads (posts, photos, post_tags) plus signing on every
scroll-back, and the row visibly drops out and pops back in each time. The same `load()` guard also
skips testing `isHidden`, so on a week where a Spotlight strip is pinned over it, the host still
performs all three reads for a row `row` can never return.

## Low

**Flim/Services/PushDestination.swift:232-242 (take())**, `take()` sets `lastTaken = nil` before
checking whether anything is even stored under `key`, so a `take()` call that finds nothing still
wipes the clock `hold()` depends on. This reopens the defect OPEN.md's 2026-09-27 row (fixed
tonight by having `take()` preserve `lastTaken`) via a different line: any intervening `take()` or
`clear()` call between the real `take()` and a later failure-triggered `hold()` of the same
destination (routine, `MainTabView.onAppear`, a `scenePhase` foreground, or
`PendingPushDestination.clear()` can all fire in between) clears `lastTaken` first, so the
subsequent `hold()` finds no `firstHeld` and restarts the 30-minute lapse clock from "now" instead
of the original hold time.

**Flim/Services/NotificationActions.swift:60-78 (performFollowBack)**, account identity is
checked once at `:63`, before the `await` on the `follows` insert. On a failure, the catch at `:74`
holds `.profile(userId: action.target)` with no re-check of the signed-in session. If the session
changes mid-request (sign-out, different sign-in) in that window, the held destination survives
and the new account's next launch navigates to a profile that belonged to the context of the
previous account's Follow-back tap. Low impact: `UserPageView` loads a profile safely for any
signed-in account, so this is an unexpected navigation, not a wrong write or data exposure.

**Flim/Views/Darkroom/SortDeckView.swift:216-224 (UpNowThumbKey), Flim/Services/FeedService+Spotlight.swift:351-356,468-478**, 
the new `UpNowThumbKey` correctly stops `refreshOwnSpotlightThumb` from running mid-send (fixing
OPEN.md's 2026-09-28 row), but `ownSpotlightThumb` only returns a thumbnail when
`ownSpotlightThumbPhotoId == ownSpotlightEntry?.photoId`, and `performPutUp`'s optimistic write
sets `ownSpotlightEntry.photoId` to the incoming frame's id immediately, before the round trip. The
cached thumbnail id still names the outgoing frame, so the identity check fails for the whole send
and the row renders a blank tile under "Up now" rather than holding the outgoing frame's picture,
contradicting the comment at `SortDeckView.swift:217-220` that says it does.

**Flim/Models/Spotlight.swift:949-980 (SpotlightSlot.slot), Flim/Views/Feed/FeedView.swift:1138 (isPinned)**, 
`slot()` returns `.top` both for the one genuinely pinned week and, separately, for ANY unseen week
when `seam == .top` (fully caught up). `isPinned` only tests `spotlightSlots[weekKey] == .top`, so
it cannot distinguish the two. A reader who is fully caught up but left last week's strip unopened
gets both last week's and this week's strips placed at `.top` simultaneously when the new week
publishes, and `spotlightStrips(in: .top,...)` renders every week whose slot is `.top`, two strips
stacked at the top of the feed, which the snapshot's own comment (`Spotlight.swift:994-995`) says
must not happen.

**Flim/Models/Spotlight.swift:1089-1092 (SpotlightSeenMark.dayKey), Flim/Views/Feed/FeedView.swift:1156**, 
`dayKey` uses a plain midnight calendar boundary, unlike every other day-filing site in this app
(`FeedUnit.dayKey`, a −4h shift). A reader who opens the feed at 23:30 Monday, 01:00 Tuesday, and
01:00 Wednesday gets three distinct midnight-keyed days, spending the 3-day "seen" allowance
(`shownDaysLimit`) and losing the strip's pinned slot, even though by the app's own day convention
those are only two nights (Monday night, Monday night, Tuesday night).

**Flim/Views/Feed/SpotlightViews.swift:425-431,446-451,489-498 (SpotlightChosenCallout)**, the
callout is derived from `feed.spotlightPastWeeks`, which a pagination sentinel keeps appending to
while scrolling, and renders inserted at the top of the week list's `ScrollView`. A viewer whose
only chosen frame is on a later archive page will have the ~106pt callout inserted above wherever
they've scrolled to the moment that page lands, shifting everything beneath their thumb. Latent
today (Spotlight has about three weeks of data, all on one page); becomes reachable once the
archive exceeds one page.

**Flim/Services/FeedService.swift:1599-1609 (tagWrittenAt/tagWriteClock), :1017-1042 (resetForAccountChange)**, 
the new tag-write clock is not cleared by `resetForAccountChange`. Account A starts a tag edit on
post P; before it lands, A signs out and B signs in, and P is also in B's feed. B's reload issues a
tags batch read; A's in-flight edit's trailing `markTagWrite(P)` (no epoch guard) then advances the
clock past B's read's start, so `applyTagRead` treats B's read as stale for P and skips writing its
tags, P shows no tag chips for B until the next reload (self-healing after one cycle, since the
clock advances no further).

**Flim/Views/Feed/FeedView.swift:958-977 (reload invite-quota refresh)**, the new refresh
unconditionally assigns `inviteQuota = quota` even when `ownInviteQuota()` fails and returns
`.unknown` (its documented fail-soft value). The empty state's gate (`FeedView.swift:906`)
deliberately shows the invite button for `.unknown`. An account with zero invites left (button
correctly hidden) pulls to refresh on a flaky connection; the RPC throws, `.unknown` overwrites the
known `.remaining(0)`, and the dead "Invite someone" button reappears, the outcome this refresh
was added to prevent in the first place.

**Flim/Views/Profile/ChapterRecapViewModel.swift:77,243, Flim/Views/Profile/ChapterRecapView.swift:464-467**, 
tonight's fix correctly excludes dead frames from `curatedDeck` even when they're a stat highlight,
but `closingLines` is built from `stats` alone, unfiltered, and the highlight's thumbnail is still
signed and shown. A month whose `longestGap` (or most-reacted/most-commented) photo is a dead frame
shows that stat row with its picture, but `onSelectPhoto`'s `deckIndex(ofPhoto:)` can't find it in
the (now dead-frame-filtered) deck and the tap silently does nothing.

**Flim/Views/Feed/FeedView.swift:136-138,689,1097-1099,1142 (spotlightStripHoldsTop vs slot snapshot)**, 
`spotlightStripHoldsTop` reads `seenSpotlight`, which `markSpotlightSeen` updates synchronously the
instant the pinned strip is opened, flipping `SpotlightClosingHost`'s `isHidden` to false right
away. But the strip's own `spotlightSlots[weekKey]` stays `.top` until the next full snapshot (a
`growOnly` pass preserves an already-anchored slot, by design, per `Spotlight.swift:983-988`). So
opening the pinned strip and dismissing its sheet un-hides the closing row directly above a strip
still rendered at the top, both Spotlight elements visible together, contradicting "one Spotlight
element there at a time."

**Flim/Views/Feed/PeopleYouKnowRow.swift:25,104-111 (per-launch picked cache)**, the new
`Self.picked` cache (tonight's fix for the row's own refetch-on-scroll bug) is never invalidated
when the viewer follows one of the three people it shows, from the row itself. Following someone
from the row, scrolling it off the `LazyVStack` and back re-runs `.task`, which returns the stale
cached pick unchanged, the now-followed account stays listed, and the row never backfills the
third suggestion a fresh fetch would have provided, for the rest of the launch.
