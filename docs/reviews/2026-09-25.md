## 1. `Flim/Services/FeedService.swift:1516` (`restore`), called unguarded from `Flim/Views/Feed/FeedUnitCard.swift:713,750` and `Flim/Views/Feed/PostDetailView.swift:336,364` (high)

A failed undo commit can insert the departing account's posts into the shared `feed` array after an account switch has already reset it.

Failure scenario: account A taps "Delete post" (or "Block" on a card/post detail). `FeedUnitCard.deleteCurrent`/`blockAuthor` snapshot the removed `FeedItem`s into `removed` and stage the delete behind `UndoCenter`, with `revert: { feedService.restore(removed) }` and no captured epoch. Inside the 5s window, A's session is lost or A signs out. `ContentView.swift:116-126`'s `onChange(of: auth.currentUser?.id)` calls `UndoCenter.shared.flush()` first, then `feed.resetForAccountChange()` on the very next line. `UndoCenter.flush()` (`UndoCenter.swift:80-85`) calls `expire(item)`, which sets `staged = nil` and spawns a new `Task { await self?.perform(item) }` (`UndoCenter.swift:105-113`); that Task body has not run yet when `flush()` returns, so `feed.resetForAccountChange()` clears `feed.feed` to empty before the commit's network call has even started. When the deferred `perform` finally runs `item.commit()` (`feedService.deletePost(id:)`, `FeedService.swift:1524-1531`), the request now runs with no session or under account B, so it fails; `perform` calls `item.revert()`, which calls `feedService.restore(removed)`, unconditionally appending A's `FeedItem` (A's author header, A's `cardPath`) back into the reset array. If this round trip outlives B's sign-in, B renders A's post on their feed; post renditions are readable by any signed-in user, so the image resolves for B. `blockAuthor`'s `removed` is every post by that author, not one, so the same race reinserts a whole author's worth of content.

## 2. `Flim/Services/RollService.swift:627-634` (`deleteRoll`) and `Flim/Services/FeedService.swift:1524-1531` (`deletePost`) (medium)

Both treat a DELETE that returns no error as proof of deletion, even though Postgrest returns 204 with zero affected rows when RLS filters the row out, and both go on to report success and finalize local side effects.

Failure scenario: a roll's creator taps Delete while an account switch completes mid-request; under the new session, `rolls: creator can delete` filters the delete to zero rows, `deleteRoll` (which has no `.select()` to detect this) returns normally, `RollDetailView.swift:852-862`'s catch is never entered, `notifications.cancelRollDevelopNotification` fires, and `dismiss()` claims success while the roll is still live server-side with its one develop-reminder channel now cancelled. `deletePost` has the same shape under `posts: delete own`: a delete filtered to zero rows still returns `true` at `FeedService.swift:1538`, so the card disappears from `feed` with no revert and no failure message while the post stays up for everyone else. `PhotoService.deletePhotosConfirmed` already fixed this exact class of bug in this same release by adding `.select("id")` and failing on an empty result (`PhotoService.swift:1690-1697`); these two call sites do not use that pattern.

## 3. `Flim/Services/RollService.swift:633,639` (`deleteRoll`, `leaveRoll`, both calling `forget`) (medium)

`deleteRoll` and `leaveRoll` write shared roll state after an await with no `AccountEpoch` guard, unlike every other mutator in this file. `setRollCover`'s own comment, added in tonight's commit, states "every other mutator in this file guards its post-await writes"; `deleteRoll`/`leaveRoll` are the two exceptions. `forget(_:)` (`RollService.swift:649-656`) removes the roll from `rolls`, `memberCounts`, `coverPaths`, ends its Live Activity, and refreshes/persists the widget snapshot. Combined with finding 2: an account switch during a `deleteRoll` call whose server delete was silently filtered to zero rows still runs `forget`, ending that account's Live Activity for a roll it still owns and rewriting the widget snapshot without it; the roll reappears on the next `fetchRolls`, but the Live Activity does not come back.

## 4. `Flim/Services/RemotePush.swift:194-218` (`detachAfterSessionLoss`) (medium)

A failed session-less token detach is logged and dropped with no persistence and no retry, unlike the sibling path (`unregisterCurrentDevice`'s catch, `RemotePush.swift:171-182`) which explicitly treats a swallowed detach failure as "a privacy leak, not just staleness" and persists `pendingDetachTokenKey`/`pendingDetachOwnerKey` for a later retry.

Failure scenario: a refresh token is revoked server-side (or the device is offline) while signed in; the SDK's `.signedOut` event fires `detachAfterSessionLoss()` as a fire-and-forget `Task` (`RemotePush.swift:202-212`); the `detach_device_token` RPC times out or the app is suspended before it completes. The function's own doc says the backstop is "a later sign-in on this device reassigns the token through `register_device_token`"; but if the phone's owner never signs back in on that device, nothing else ever retries the detach, and the `device_tokens` row survives. The departed account's develop/social/digest pushes keep landing on a phone nobody is signed into.

## 5. `Flim/Views/Camera/CameraViewModel.swift:832-836` (`sessionInterruptionEnded`'s else-branch) (low)

The detached stop issued when an interruption ends while the tab is not showing does not re-check `wantsSessionRunning` before it runs, unlike `finishRestart` which does.

Failure scenario: a call interrupts the camera session while the Camera tab is open; the user switches to Feed (`stopRunning` sets `wantsSessionRunning = false` and returns early because an interrupted session already reports `isRunning == false`, so no explicit stop is issued); the call ends, queuing `Task.detached { if session.isRunning { session.stopRunning() } }`; the user taps back to Camera inside that scheduling window. `startRunning()` sets `wantsSessionRunning = true` but returns at `guard !session.isRunning` since AVFoundation already auto-resumed the session, so no restart is issued; then the queued detached task stops the session anyway. `isInterrupted` was already cleared, so the unavailable overlay is gone and the shutter looks live over a frozen frame; every tap silently no-ops at `capturePhoto`'s `guard session.isRunning` until the tab is left and reopened. The window is narrow (one Task's scheduling latency), hence low rather than medium.
