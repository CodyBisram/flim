## 1. Flim/Services/FailedUploadStore.swift:104

Retrying a failed upload silently discards the capture's quality, phash and is_miss values and
writes them to the database as NULL/false, even though they were already computed before the
upload failed.

`FailedUpload` gained `quality`, `phash` and `isMiss` fields in this diff, and its doc comment
(line 29-31) claims they are "carried the same way as sharpness" through the on-disk sidecar. The
private `Sidecar` Codable struct used for persistence (lines 104-116) was not updated to include
them: it still only has `burstGroup` and `sharpness`. `save()` (line 133-136) builds a `Sidecar`
without the three new fields, so they never reach disk, and `load()` (line 156-167) reconstructs
`FailedUpload` from the decoded sidecar without passing them, so they come back nil/false via the
initializer defaults regardless of what was originally scored.

Failure scenario: a shot is taken, `BurstDetector.analyze` scores it (quality, phash, and
possibly isMiss=true for a dead frame), the network call fails, and `PhotoService.captureAndUpload`
queues it via `failedUploadStore.save`. On the next retry, `PhotoService` builds
`BurstDetector.Decision` straight from `pending.quality`/`pending.phash`/`pending.isMiss`
(PhotoService.swift:340-343), all now nil/false because the round trip through `Sidecar` dropped
them, and that decision is what gets written into the `InsertPhoto` payload actually inserted into
`photos`. A genuinely black or smeared frame that failed to upload on the first try loses its
dead-frame label permanently (never shown as "Missed?", never excluded from chapter curation or
roll-reveal playback), and any retried photo permanently has NULL quality/phash in the database,
which also forces `ChapterCuration.columnCandidates` to fall back to the slow Vision path for the
whole month it belongs to, defeating the new fast path for every other photo in that month too.
This path is not an edge case: `retryFailedUploads` (same session) and `restoreFailedUploads`
(next launch) are the standard way a failed capture ever reaches the server.

Severity: high.

## 2. Flim/Services/ChapterCuration.swift:154

In a month that mixes photos from before and after 2026-09-08, any photo that already carries a
stored `quality` value never gets a feature print computed, so the diversity/duplicate check
treats it as unrelated to every other photo, defeating deduplication specifically for the newest
photos.

`curate()` falls back to the per-photo Vision path (line 69-75) whenever any single photo in the
month is missing `quality` or `phash`, which is the case for every month that spans the
2026-09-08 rollout. In that path, `qualityScore(for:)` returns early at line 154
(`if let stored = photo.quality { ...; return stored }`) for any photo that already has a stored
quality value, before ever reaching the `VNGenerateImageFeaturePrintRequest` call that populates
`featurePrints[photo.id]` (lines 166-173). Back in `curate()`, the similarity closure at
line 108-109 does `guard let printA = prints[a], let printB = prints[b] else { return 0 }`, so any
photo without a cached feature print is scored as 0 similarity (`ChapterCurator`'s "nothing
alike") against everything, including genuine near-duplicates.

Failure scenario: a September 2026 chapter has some photos from before the rollout (no stored
quality) and several new photos from a single burst (each with a stored quality, all visually
near-identical). Because of the one legacy photo, `columnCandidates` returns nil and the month
takes the Vision path. Each new-schema burst photo short-circuits to its stored quality without a
feature print, so `ChapterCurator.select`'s greedy diversity step (ChapterCurator.swift:57-58)
computes `maxSimilarityToPicked = 0` for all of them no matter how similar they actually are, and
two or more near-duplicate frames from the same burst can both end up in the 15-photo recap deck,
which the diversity rule exists specifically to prevent.

Severity: medium.
