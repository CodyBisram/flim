## 1. low, supabase/functions/send-one-shot-push/index.ts:884 (`spotlightLastCallCohort`)

The `hasFrame` cohort query's `.or(...)` filter is broader than what is actually postable to
Spotlight this week, so some recipients get the Darkroom-branch copy and a deep link into a
Darkroom with nothing they can send.

Branch one of the filter, `taken_at.gte.${start}`, has no upper bound on `develops_at` at all, so
a frame taken this week but not yet developed (`develops_at` still in the future, pinned to a
later `rolls.reveal_at`) counts as `hasFrame`. Branch two, `develops_at.gte.${start},develops_at
.lte.${now}`, has no bound tying `develops_at` back to `taken_at`, unlike
`_spotlight_frame_fits_week` (schema.sql:16764-16780), which only allows the develops-this-week
path when `develops_at <= taken_at + INTERVAL '8 days'`; a frame whose roll developed this week
more than 8 days after it was shot also counts as `hasFrame` here but would be refused
`not_this_week` by `put_up_for_spotlight`.

Failure scenario: a user shoots into a shared roll Sunday afternoon with `reveal_at` Monday
afternoon (after the Spotlight week closes Monday 04:00 ET). `taken_at >= start` matches, so they
land in the `hasFrame` branch and get "Post your best frame from this week and send it to
Spotlight. It goes up tomorrow." deep-linked to the Darkroom, where the frame isn't developed yet
and nothing is postable. The camera-branch copy ("There's still time. Shoot something good
tonight...") was the one that fit. Not a double-send and not a never-send, just the wrong variant
and a dead-end route, once per affected recipient per week this push runs.

## 2. low, Flim/Views/Feed/UserPageView.swift:481-485 (`onChange(of: deskLayout)`)

Someone else's seal card only moves from the Duo's docked column back to a full-screen cover when
folding (`layout != .open`); nothing moves it the other way when unfolding into the open layout,
so a card opened on a single display and then unfolded stays a full-screen cover spanning both
halves of the open display instead of docking to the right of the fold like `dockedSealCard`'s own
doc comment (line 74) says it should.

Failure scenario: on a Duo folded shut, open someone else's profile and tap a seal
(`presentSealCover`, line 1107, sets `coverSealCard`). Unfold the device. `deskLayout` becomes
`.open`; the only handler watching that change (line 481) guards on `layout != .open` and does
nothing here, so `coverSealCard` is still set and the `fullScreenCover(item: $coverSealCard)` at
line 565 keeps covering the whole open display instead of the drawer-docked presentation the open
layout uses everywhere else on this page.

## 3. low, Flim/Views/Feed/UserPageView.swift:470-474 (`onChange(of: docksMonths)`)

Folding the Duo while your own Seals drawer is docked and a card is open inside it discards that
open card with no transfer to the sheet it falls back to.

`dockedSeals` is a `SealsDrawer` (`SealsSheet.swift:9-35`) that tracks `openKind`, the seal whose
card is open inside the drawer. On fold, line 472-474 sets `dockedSeals = nil` (dropping the
instance and its `openKind` entirely) and sets `showBadgePicker = true`, which presents a fresh
`BadgePickerSheet` (line 561) with no parameter carrying over which card was open. Folding the Duo
while reading your own open seal card's description silently closes that card back to the
drawer's grid, with no equivalent path preserving it the way `dockedSealCard` (finding 2's
variable) is at least carried across in the someone-else's-seal-card case.
