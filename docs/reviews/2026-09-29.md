## 1. `Flim/Views/Main/MainTabView.swift:649` (medium)

A new account that denies the camera permission during onboarding is never asked for notification
permission, on any later run.

`maybeShowNotifPrimer()`'s guard is `guard hasOnboarded, hasSeenCameraCoach else { return }`. The
only writer of `hasSeenCameraCoach` is the camera coach's "Got it" tap
(`Flim/Views/Camera/CameraView.swift:850`), and the coach only renders in the branch taken when
`camera.permission != .denied` (`CameraView.swift:232-266`); when permission is `.denied`,
`cameraDeniedOverlay` renders instead and the coach never mounts.

Failure scenario: a new account denies the camera prompt at onboarding. The Camera tab keeps
showing `cameraDeniedOverlay`, `hasSeenCameraCoach` stays `false` forever, and every call site of
`maybeShowNotifPrimer` (onboarding completion, the coach's own `onChange`, and the tab's `onAppear`)
is gated on a key that can never become true for this account. The soft notification ask, the only
path to `UNUserNotificationCenter` authorization for a new account per the surrounding comment, is
never presented, and `didDecideNotifPrimer` never gets the "iOS already answered" reconciliation in
the same function either.

## 2. `scripts/asc_watch.py:86-95` (low)

A push that fails to send on the exact tick the App Store review finishes is never retried, and the
watch exits believing it told the owner.

`notify()` catches every exception and only prints (`scripts/asc_watch.py:47-51`), but `main()`'s
loop advances `last = state` unconditionally right after calling it (line 92), and returns
immediately when `state in DONE` (line 93-95) with no further chance to notify.

Failure scenario: the poll sees `READY_FOR_DISTRIBUTION` (the build going live), the notify-owner
function cold-starts or drops that one request, `notify` prints "notify failed" and swallows it,
`last` is set to `READY_FOR_DISTRIBUTION`, and the function returns because the state is in `DONE`.
The workflow run ends successfully; nothing else is scheduled to check this version again, and the
owner is never told the release went live.

## 3. `Flim/Services/FeedService.swift:1523` (low)

A tag read started before a tag edit can land after it and erase the edit until the next full
reload.

`applyTagRead` now assigns every requested id unconditionally (`tagsByPost[id] = read.tags[id] ??
[]`, changed from a merge to fix audit A-3 in 1.6.1), with no per-post read generation. `setTags`
finishes by calling `loadTags(for: postId)`, but nothing stops an earlier, still in-flight
`loadTags(for postIds:)` batch read (e.g. from `refreshOwnSpotlight`'s foreground reload) from
resolving after it.

Failure scenario: the app foregrounds and starts a batch tags read for on-screen posts; within that
window the user adds a tag to one of those posts, and `setTags`'s own read completes and renders the
new chip; the earlier batch read then lands, reassigns `tagsByPost[postId]` to the pre-edit list, and
the tag chip disappears (Spotlight's "Put it up" re-enables as untagged) until the next full reload.

## 4. `Flim/Services/FeedService.swift:1696-1700` (low)

A comment kept after a failed re-read can be attributed to `@someone` instead of its actual author.

The fallback `CommentInfo` built when `fetchComments`'s re-read fails looks up the author by
scanning `commentsByPost.values` for an existing comment from the same `userId`
(`FeedService.swift:1696-1700`); `CommentInfo.handle` falls back to `"@someone"` when no author is
found (`Flim/Models/Social.swift:166`).

Failure scenario: a user posts their first comment anywhere on a post, the insert succeeds, but the
`fetchComments` re-read fails (offline mid-send). No cached comment from that user exists anywhere
to source an author from, so the kept comment renders under "@someone" instead of the poster's own
handle.

## 5. `Flim/Views/Feed/FeedUnitCard.swift:817-822` and `Flim/Views/Feed/PostDetailView.swift:517-522` (low)

A reaction-failure toast can be dismissed early by an unrelated, earlier failed reaction's timer.

`react(_:userId:)` sets `reactionFailedToast = true` on a failed write, sleeps 2 seconds in its own
unkeyed task, then sets it back to `false`, with no cancellation of a prior pending dismissal (the
same class of bug already fixed for `ProfileView.photoError`, see `docs/reviews/OPEN.md`).

Failure scenario: offline, tap-react on emoji A at t=0 (fails, toast shown, dismiss scheduled for
t=2); tap-react on emoji B at t=1.5 (fails, sets the same toast flag true again). A's timer fires at
t=2 and clears the toast B's failure was still meant to be showing, 1.5 seconds early.
