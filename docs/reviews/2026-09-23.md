## 1. Flim/ContentView.swift:234 — the offline reveal-completion retry is wired to backgrounding, not foreground, so it misses the common case entirely (high)

`RollService.flushPendingRevealCompletions()` documents its own cadence: "Called from this
account's activation path (`restore(for:)`) and on every foreground, the same cadence as
`FeedSeenStore`'s own pending flush" (`Flim/Services/RollService.swift:473-476`). But in
`ContentView.swift` the call sits inside `guard phase == .active else { ...; return }` at line
234, alongside `UndoCenter.shared.flush()` and `FeedSeenStore`'s pre-background flush, i.e. it
fires when the scene phase stops being active (backgrounding), not when it becomes active. The
genuine foreground branch below (refreshVersionGate, tab signal refresh, the autosave sweep,
`photos.retryFailedUploads()`) never calls it.

Failure scenario: `completeRevealView(rollId:)` queues the roll id in
`pendingRevealCompletions.<userId>` when the `complete_reveal_view` RPC fails (offline, or a
transient error). The person keeps using the app; connectivity returns while the app stays
foregrounded (an ordinary lock/unlock does not toggle scenePhase away from `.active` at all, and
even a brief backgrounding runs the flush at exactly the worst moment: `flushPendingRevealCompletions`
spawns bare `Task`s with no `BackgroundKeepAlive` wrapping, so iOS can suspend them mid-request).
The completion sits unflushed for the rest of the session — reachable again only on the next
`restore(for:)` (a fresh sign-in/session resolution, not just reopening the app) — leaving the
server's `completed_at` null and risking the reveal re-presenting on another device signed into
the same account, the exact failure this durability queue (05cd8bd, and re-hardened by 05aa8e6
tonight) was built to close.

Severity: high

## 2. Flim/Services/WidgetSync.swift:26-52 — `clear()`'s cancellation of a prior `refresh()` stops being effective once that refresh is already running, so a departing account's data can be written back after `clear()` (medium)

`refresh()` debounces via `pending = Task.detached { sleep(700ms); guard !Task.isCancelled else
return; await run() }`; `Task.isCancelled` is checked exactly once, immediately after the sleep.
`clear()` (line 46) calls `pending?.cancel()`, but once `run()` has passed that single check and
is executing `compose()` (three concurrent Supabase round trips, `Flim/Services/WidgetSync.swift:77-93`),
nothing inside `run()` or `compose()` checks cancellation again, so `.cancel()` has no effect on
it. `compose()` also reads the account once, at its own start (`try? await
supabase.auth.session.user.id`), and never re-checks it.

Failure scenario: an action shortly before sign-out (e.g. `completeRevealView`, which itself
calls `WidgetSync.refresh()`) starts the 700ms-debounced `run()`. Within the next several hundred
milliseconds — while `compose()`'s reads are still in flight, which routinely still succeed since
a locally-cleared session does not retroactively invalidate an already-valid JWT the in-flight
requests were dispatched with — the person signs out or deletes the account. `AuthService`
posts `.flimAccountDidChange`, which `ContentView.swift:187` answers with `WidgetSync.clear()`,
writing an empty snapshot immediately. The earlier `run()` then finishes, finds its composed
(departing-account) snapshot different from the just-cleared one, and calls `WidgetStore.write`
with the departing account's real unsorted count, developing roll, and memories — undoing
`clear()`. Whoever uses the device next sees the previous account's data on the home-screen
tiles, the exact leak `clear()` (05aa8e6, tonight) was added to close. This codebase already has
a documented pattern for exactly this class of race (`AccountEpoch`, used by `AuthService.setAccent`
per a prior finding on this ledger); `WidgetSync` has no equivalent guard.

Severity: medium

## 3. Flim/Views/Darkroom/DarkroomZoomRows.swift:322 — a fifth Gregorian-parsing site was missed in tonight's fix, so the All-time row can mislabel months on a non-Gregorian device calendar (medium)

Tonight's commit (05aa8e6) fixed four `Calendar.current` sites that were reading a Gregorian
`Date` back through the device's own calendar: `DarkroomMonthSummaryV2.parseMonthStart`,
`DarkroomView.dateFromYearMonth`, `DarkroomZoomRows.monthName` (line 311, now explicitly
`Calendar(identifier: .gregorian)`), and `ChapterRecapView.heroDateStamp`. Eleven lines below the
fixed `monthName`, `DarkroomAllTimeRow.init(totals:monthSummaries:...)` still opens with `let
calendar = Calendar.current` (line 320) and uses `calendar.component(.month, from:
$0.monthStart)` to key `shotsByMonth`/`topCoverByMonth`, where `$0.monthStart` is exactly the
Gregorian-corrected `Date` `parseMonthStart` produces. This initializer is live: `DarkroomView.swift:803`
calls it with real server `monthSummaries` for the "All-time" rung.

Failure scenario: on a device set to a calendar whose month numbering diverges from Gregorian
(Hebrew, Islamic, Persian, Chinese — Buddhist and Japanese stay Gregorian-month-compatible),
`calendar.component(.month, from:)` returns a non-Gregorian month number for each summary row.
The `ForEach(1...12)` grid in the same file looks up `shotsByMonth[$0]`/`topCoverByMonth[$0]` by
Gregorian month numbers 1-12, which no longer match the dictionaries' keys, so the All-time row
silently shows a wrong or missing shot count and cover for some or all months.

Severity: medium
