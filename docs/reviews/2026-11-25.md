## Flim/Services/FeedService.swift:494-509, medium

`declineRequest` discards the `decline_friend_request` RPC's returned `Bool` and unconditionally
treats the call as a success.

Failure scenario: phone A has the Requests tab open showing X as a pending request. On phone B
(same account) the follow is accepted or X follows back first, so X is now a mutual friend
server-side. Phone A's `followerIds` is stale and still renders X under "WANT TO BE FRIENDS".
Tapping Decline calls the RPC; the server's `NOT EXISTS ... mine` guard (pinned by the
migration's own test, "B cannot 'decline' C: they are friends -> false") refuses and returns
`false`. The client never reads that `false`, it removes X from `followerIds` anyway and
reports success with no error. X remains a friend on the server while phone A shows them in
neither Requests nor Friends (`friends` requires `followsMe`), and their profile reads "Add
friend", until the next successful `loadFollowers`.

## Flim/Views/Feed/DeskFriendsView.swift:291-300 and Flim/Services/FeedService.swift:508, medium

A successful decline is never written through to `feed.friendsLists` or persisted via
`persistGraph()`; only the view's local `followers` array and `FeedService.followerIds` are
mutated.

Failure scenario: decline X (server genuinely deletes the row), tap Done, reopen Friends. The new
`DeskFriendsView` instance hits `load()`'s cache-first branch, which restores `feed.friendsLists`
still containing X, and `incoming` filters only on `!feed.isFollowing`, not `followsMe`, so X
reappears under "WANT TO BE FRIENDS" with Add/Decline until the background fetch lands, and
`load()` re-persists that stale list to disk in the meantime. If the fetch fails, the row sticks
permanently (the same mechanism as the open 2026-11-19 DeskFriendsView row, reached through a new
feeder site).

## Flim/Views/Feed/UserPageView.swift:472-483, low

The fold handoff added for the docked Seals drawer has no symmetric unfold branch.

Failure scenario: on the Duo's open display, own page, docked Seals open with a card showing.
Fold: `onChange(of: docksMonths)` moves the drawer into `handedOffSeals` and presents it as the
`BadgePickerSheet`. Unfold: the same handler has no `docks == true` branch, so `handedOffSeals`
and `showBadgePicker` never reset, the sheet keeps covering the full-screen display instead of
redocking, while the page behind it renders the two-column layout with `dockedSeals == nil`. The
sibling handler two blocks below (`onChange(of: deskLayout)`, for someone else's seal card) does
handle both directions; this one was only given the fold half.
