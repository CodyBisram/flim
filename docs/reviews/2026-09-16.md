## 1. supabase/migrations/2026-09-15_post_release_ops.sql:19-37 (copy_edge_failures)

The new hourly ledger copy watermarks on `MAX(id)` already copied into `edge_response_log`, not on which `net._http_response` ids have actually landed, so a slow failing request can be permanently skipped once a faster failure with a higher id is copied first.

Failure scenario: `net._http_response` rows appear only when a pg_net request completes, keyed by the id assigned at submission time, so completion order does not track submission order. `pi_hook_notify` fires on every insert into `crash_diagnostics`, `ops_alerts`, `user_reports`, `users`, and `activation_events` with a 5s timeout, so it can produce a burst of fast-completing rows. A slower edge-function invocation (the same migration's own comment notes "the social push can take 200s when it has work") can be queued with a lower id just before that burst. If several of the fast `pi_hook_notify` failures land and get copied first, `flim-edge-ledger`'s watermark advances past their ids. When the slow request finally completes and fails or times out, its id is lower than the new watermark, so `id > COALESCE((SELECT MAX(id) FROM public.edge_response_log), 0)` excludes it on every subsequent run: it never enters `edge_response_log`, and `edge_non_200_24h`/`edge_timeouts_24h` in `nightly_numbers()` silently undercount that failure forever. This is exactly the class of failure the ledger exists to catch (a slow, ultimately-failing edge function call), and it drops silently with no trace anywhere else in the system.

Severity: medium.
