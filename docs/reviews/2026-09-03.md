## Flim/Views/Darkroom/PhotoGridCell.swift:371 (severity: high)

`load()`'s disk-cache-miss path resumes from an await with no `loadGeneration` guard, so a stale call can overwrite a newer call's already-loaded image with nil.

Failure scenario: a `CachedImage` cell has `cacheKey` set and the id (`cacheKey|url|maxPixel`) changes twice in quick succession, for example a fast resize of the measured width described in the `.task(id:)` comment at line 360, or rapid scrolling that re-resolves a signed URL. Call A starts, misses the in-memory cache, and suspends at `await DiskImageCache.load(...)` on line 371 while the disk read is still pending. Before it resumes, the id changes again, `loadGeneration` is bumped, and call B starts, hits the in-memory cache synchronously, and sets `uiImage`/`shown` to the correct image with no further await. Call A then resumes with a disk-cache miss (nil), falls through line 377 to lines 382-383 (`uiImage = nil; shown = false`) with no generation check, wiping out the image call B just set. Call A's subsequent `await ImageLoader.fetch` for its own (stale) URL later completes and hits the `generation == loadGeneration` guards at lines 385/390, which correctly stop it from writing again, but nothing restores call B's image: the cell is left blank until its `.task(id:)` id changes again (which may not happen if the cell scrolls out and simply stays at that id, or is a non-lazy persistent view).

## Flim/Services/RollSnapshotStore.swift:232 (severity: low)

`save()` writes each snapshot from an independent, unordered `Task.detached`, so two `persistSnapshot()` calls for the same account can finish out of order and leave the on-disk file reflecting an older in-memory state than the one that actually persisted last logically.

Failure scenario: two mutations for the same signed-in user happen close together (for example `setRollCover` followed quickly by `forget`, or two `fetchRolls` responses landing back to back). Each calls `persistSnapshot()`, which synchronously reads the current `rolls`/`coverPaths` and hands them to a freshly spawned `Task.detached`. The scheduler is free to run those detached tasks in either order, so the write started for the earlier state can finish after the write started for the later state, leaving the JSON file on disk one mutation behind. This only affects the next cold-launch restore (`RollSnapshotStore.load`), not any in-memory state, and self-heals on the next successful `fetchRolls`, so the practical impact is a roll list or cover that is briefly one step stale on the very next launch.
