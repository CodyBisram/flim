# Review notes for 2026-11-12

Range: bb72562..d371022 (main), two commits: the 1.7 camera's layout rebuilt onto 1.6's structure
(roll/timer/flash on top, full-width frame, shutter below), then a pass of fixes from a design
review of 1.7. All findings below sit behind `AppInfo.is17`, on only in the Beta configurations.

1. **Flim/Views/Feed/UserPageView.swift:1602-1617** (high). A re-follow made inside the 5-second
   undo window of an unfollow is silently reversed. Tapping the "Friends ✓" chip
   (`AppInfo.is17 && following`) removes `followingIds` optimistically and stages the real
   `unfollow` via `UndoCenter.shared.stage(...)` with no `key:`, so nothing can supersede it. The
   button does not set `busy = true` on this path, so it stays tappable. Failure scenario: tap
   "Friends ✓" on a mutual (t=0, unfollow staged); within 5s tap the same control again, now
   reading "Add friend" (`following` already flipped false), this runs `feed.follow`, whose
   insert hits the still-present server row and gets `23505`, which `FeedService.follow` treats as
   success (`FeedService.swift:352-358`), so the chip shows "Friends ✓" again. At t=5s the
   original staged commit still fires regardless, calling `service.unfollow` and deleting the
   follow row for real; `unfollow`'s own optimistic removal flips the chip back to "Add friend"
   with no error and no further capsule. The user's second, later action (re-following) is
   discarded without any indication of what happened.

2. **Flim/Views/Feed/UserPageView.swift:1602-1617 (FollowButton), hosted at
   Flim/Views/Feed/DeskFriendsView.swift:116** (medium). Unfollowing from the Friends sheet shows
   no capsule and, on failure, no notice. `undoCapsuleHost()` is only attached to `MainTabView`'s
   own content (`MainTabView.swift:435,497`); `DeskFriendsView` applies `.flimSheetSurface()`
   (`DeskFriendsView.swift:77`) with no capsule host of its own, and a `.sheet` draws over the tab
   view's overlay. Failure scenario: open You → Friends, tap "Friends ✓" on a row; the row
   disappears from the list with no "Removed as a friend" capsule and no visible Undo. If the
   staged `commit` then fails (offline), `UndoCenter`'s revert puts `followingIds` back and calls
   `onFailure`, but `DeskFriendsView`'s own `showNotice` path is unreachable behind the sheet (no
   host renders it), so the row silently reappears with no explanation of why.

3. **Flim/Views/Main/DeskNotificationPrimer.swift:19-59** (medium). The notification primer's
   content can render squeezed into roughly half the sheet even at the default text size. The
   `ScrollView` (line 19) and the retained `Spacer(minLength: 12)` (line 58) are both flexible
   siblings with equal (default) layout priority in the outer `VStack`, so the stack's leftover
   height after the two buttons is split roughly evenly between them rather than given to the
   scroll content. Failure scenario: on a typical phone, the ~420pt of heading/body/three sample
   rows scrolls inside a viewport roughly half that height, with a similarly-sized blank gap
   sitting above the "Turn on notifications" button, at default Dynamic Type, not only at
   accessibility sizes. `DeskUpdateCard.swift:26-60` avoids this by not pairing the `ScrollView`
   with a `Spacer`.

4. **Flim/Views/Darkroom/DarkroomView.swift:525-529** (low). `DeskChrome.shared.selecting` can
   desync from the Darkroom's own `isSelecting` state after a tab switch. `onDisappear`
   unconditionally sets `selecting = false`; `onChange(of: isSelecting, initial: true)` only
   re-fires on an actual change to `isSelecting`, not on reappearance. Failure scenario: enter
   select mode in the Darkroom (tab bar replaced by the Select bar), switch to another tab
   (`onDisappear` fires, flips `DeskChrome.shared.selecting` to false, tab bar space reserved
   again), switch back to Darkroom, `isSelecting` is still true but `DeskChrome.shared.selecting`
   is false, so the floating tab bar and the Select bar both reserve space and can render at once.

5. **Flim/Views/Camera/CameraView.swift:478-486** (low). The first-shot coaching hint can be
   dismissed by a tap that also fires a focus/exposure lock underneath it. `deskFirstShotHint` sits
   in the same bottom overlay as `DeskZoomDial`, which calls `.reportsControlRegion()`
   (`CameraView.swift:483`), but the hint itself does not. `CameraPreview`'s tap recognizer only
   excludes touches inside a reported control region (`CameraPreview.swift:116-121`). Failure
   scenario: on first launch, tap the coaching hint to dismiss it, the tap also reaches the
   preview's focus gesture, locking focus/exposure near the bottom of the frame and firing a
   reticle flash and haptic the user did not intend.
