## 1. `Flim/Views/Darkroom/SortDeckView.swift:747` (medium)

Opening the sort deck can silently swap out a frame put up from another device, with no warning.

`load()` only starts a Spotlight-entry read when `currentSpotlightEntry == nil` (line 747).
`currentSpotlightEntry` (line 518) returns the entry whenever `feed.ownSpotlightEntry` is already
known and its week has not closed, including a cached "nothing up this week" entry (an
`OwnSpotlightEntry` with `postId == nil`) left over from an earlier Feed visit. Nothing else
refreshes `feed.ownSpotlightEntry` while the deck is a full-screen cover: `FeedView.reload()` is the
only other caller, and it does not run for an ordinary foreground.

`putUpFromSession` (line 611) is supposed to catch this at the tap: `if
currentSpotlightEntry.map({ ($0.postId != nil) != shownSwap }) ?? true { await
feed.refreshOwnSpotlightEntry() ... }`. But it reads the exact same stale `currentSpotlightEntry`
the sheet was built from, so the comparison is always false and the refresh, and the whole
`.frameUpChanged` re-check, never run.

Failure scenario: an account opens the Feed at 09:00 on one phone (entry read: nothing up this
week). At 10:05 the same account puts up frame X from an iPad. At 10:10 the phone opens the
Darkroom sort deck without visiting the Feed again, sorts to the end, and the session sheet reads
"Put it up for Spotlight?" with no swap warning, because the deck still believes nothing is up. The
tap sends the put-up RPC; `put_up_for_spotlight`'s `ON CONFLICT (user_id, week_key) DO UPDATE`
takes frame X down and puts the new one up. The sheet's own success copy then contradicts itself:
the title reads "Up for Spotlight" (built from the stale, non-swap `isSwap`) while the status line
reads "Swapped into Spotlight. Your earlier frame came down." The swap was never shown or
consented to.

## 2. `Flim/Models/Spotlight.swift:636,646,854-855` (rendered at `Flim/Views/Feed/SpotlightViews.swift:705-707`) (low-medium)

The session sheet's "can't go up" line names the wrong week for frames shot more than a week ago.

`makeSessionOffer` counts `shotBeforeThisWeek` for any frame with `frame.photo.takenAt <
entry.weekStartsAt` (line 636), with no lower bound, but attaches only
`SpotlightWeekLabel.previousWeekKey(entry.weekKey)` (line 646) — exactly one week back — and
`shotBefore(previousWeekKey:)` (line 854) states that week as fact: "Frames shot in \(week) can't
go up now."

Failure scenario: on 2026-09-30 (current Spotlight week starting 2026-09-28), a user develops and
sorts a roll shot on 2026-09-05, three weeks earlier. The sheet reads "Frames shot in the week of
September 21 can't go up now." — a week the user shot nothing in, and not the week the excluded
frames were actually shot.

## 3. `Flim/Views/Darkroom/SortDeckView.swift:596,631` (low)

A swap reached via `putUpFromSession`'s frame-changed path never spends the week's one-swap
allowance, so a second swap sheet can be offered later the same week.

`sessionSheetAppeared` (line 596) records `recordSwapShown` only when `offer.isSwap` — the
original offer's kind, gated on `shownOffer?.id != offer.id`. `putUpFromSession` can set
`session.kindOverride = .swap` (line 631) after a `.frameUpChanged` refusal, which changes the
sheet's live kind (`session.kind(offer)` = `kindOverride ?? offer.kind`) without changing
`offer.id`, so `sessionSheetAppeared` never re-fires and the swap is never recorded as shown.

Failure scenario: a sort ends with a `.putUp` offer; a day-boundary foreground reload refreshes the
entry mid-sheet and it now holds a frame; the next tap returns `.frameUpChanged`, and the sheet
re-titles to "Swap it in for Spotlight?" with an Up-now row. The user declines. `swapOffered` is
still false, so a later sort the same week offers a second swap sheet, when only one was meant to
be offered after a put-up. This is currently masked by finding 1 (the entry rarely refreshes at
all), and becomes reachable once that is fixed.

## 4. `Flim/Views/Feed/SpotlightViews.swift:745-746` (driven by `Flim/Views/Darkroom/SortDeckView.swift:193`) (low)

During a swap's network round trip, the "Up now" row shows the incoming frame's thumbnail under
the outgoing frame's day label.

`performPutUp`'s optimistic write sets `feed.ownSpotlightEntry.photoId` to the new photo before its
await resolves, which retriggers `.task(id: feed.ownSpotlightEntry?.photoId)` and
`refreshOwnSpotlightThumb`, replacing the held thumbnail with the incoming frame's. The "Up now"
row is still rendered from the offer's frozen `fromDay` string for the duration of the send.

Failure scenario: a swap send that takes about a second shows "Up now: your frame from Tuesday"
above a tile that fills in with the frame currently being sent up, not the outgoing Tuesday frame
— the row names the wrong photograph until the request completes.
